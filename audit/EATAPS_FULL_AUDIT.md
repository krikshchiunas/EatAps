## Границы аудита

**Что выполнено:** сплошное чтение кода (73 компонента, 64 модуля, 8 серверных точек, 12 535 строк SQL, 24 миграции, service worker, конфигурация); запуск `npm test`, `npm run build`, `npm audit` и всей SQL-оснастки проекта; прогон расчётных модулей на 15 наборах граничных данных; автоматический разбор всех 80 `useEffect` и всех 148 определений функций SQL.

**Чего аудит НЕ делал:**

- Ни один запрос к боевым адресам не отправлялся. Данные реальных пользователей не затрагивались.
- Браузерного прогона интерфейса не было — в окружении нет Chromium и средств автоматизации.
- Живого Postgres не было: политики RLS проверены разбором предикатов, а не выполнением запросов от имени разных пользователей.
- Боевое окружение Vercel недоступно — какие переменные там заданы, неизвестно.
- Живых прогонов AI-модели не выполнялось.
- Нагрузочного тестирования, проверки на устройствах, Lighthouse и замеров контраста не было.

**Статусы:** `CONFIRMED` — доказано исполнением, выводом инструмента или однозначным чтением. `PROBABLE` — путь рассуждения проверен по коду, сценарий не воспроизводился.

## Что сделано хорошо

- RLS включён на **всех 33 таблицах**; таблица промокодов намеренно оставлена вовсе без политик — закрыта по умолчанию.
- Все функции `SECURITY DEFINER` объявлены с `set search_path = public` — проверка сплошная, по всем 148 функциям.
- Подмены личности нет нигде: реакции, сообщения, подписки и настройки опираются на `auth.uid()`, а не на идентификатор из запроса.
- Уведомления невозможно подделать: политики INSERT нет вовсе, `push_notification` отозвана у роли `authenticated`.
- Гашение промокодов защищено на двух уровнях: `SELECT … FOR UPDATE` и `CHECK (used <= max_uses)` в таблице.
- Синхронизация между устройствами — гибридные логические часы, тумбстоуны, пофайловые метки, кэш по пользователю, атомарный compare-and-swap по `revision`.
- Service worker не кэширует ничего приватного: чужие origin и `/api/` пропускаются мимо кэша.
- Из 80 проверенных `useEffect` **ноль** оставлены без функции очистки.
- XSS-поверхности нет: ни `dangerouslySetInnerHTML`, ни `innerHTML`, ни `eval`.
- Ограничения частоты на изменяющие действия реализованы триггерами в базе, а не в интерфейсе.
- Сканер штрихкода обрабатывает все шесть ветвей отказа, в каждой есть выход «Добавить вручную».
- Собственная оснастка вокруг SQL под автотестами: сборка, идемпотентность, аудит политик, каталог схемы.
- 814 автотестов, включая сценарии на два устройства и защиту от воскрешения удалённых записей.

## Находки подробно

### SEC-001 — Дневной лимит AI обходится параллельными запросами: проверка и списание не атомарны

**P1** · CONFIRMED · уверенность HIGH · Обход лимита / расход средств

- **Где:** `api/ai/_shared.js:88-104 (recordSpend), api/ai/chat.js:37-76, api/ai/vision.js:44-82`
- **Затронутый поток:** AI-ассистент → бюджет тарифа

#### Суть

Порядок «прочитать расход → проверить остаток → зарезервировать» не атомарен. `spentThisPeriod()` читает потраченное, `checkBudget()` решает по прочитанному, и только потом `reserve()` списывает. Между чтением и списанием любое число параллельных запросов проходит проверку по ОДНОМУ И ТОМУ ЖЕ остатку.

Инфраструктура для атомарной проверки уже есть и работает: RPC `ai_usage_add` выполняет `insert … on conflict do update` и возвращает новый итог (`returning spent_micro into v_total`). Но `recordSpend` деструктурирует только `{ error }` и ВЫБРАСЫВАЕТ `data`. Значит вызывающий код физически не может узнать, что резерв увёл счёт за потолок, и не отменяет запрос.

#### Доказательство

```
Проверено по коду:
• `ai_usage_add` возвращает bigint — новый spent_micro (setup_all.sql, миграция 2026-08-24_ai_usage).
• `recordSpend` — `const { error } = await admin().rpc(...)`; `data` не читается, наружу уходит только true/false.
• `reserve()` — тонкая обёртка над `recordSpend`, тоже возвращает булево.
• В chat.js/vision.js результат резерва проверяется лишь на «записалось или нет», а не «влезли ли в бюджет».

Арифметика для FREE (вычислено запуском src/lib/aiBudget.js):
  дневной лимит = floor(0.5 $ × 1e6 / 30) = 16 666 микродолларов
  один chat-запрос (вход ~1000 токенов, Haiku) = 1000×1 + 700×5 = 4 500
  легальных запросов в день = 3
```

#### Воспроизведение

```
1. Войти любым обычным аккаунтом (тариф FREE).
2. Взять access_token из сессии Supabase.
3. Отправить 100 запросов POST /api/ai/chat ОДНОВРЕМЕННО (Promise.all / xargs -P 100), а не последовательно.
4. Все 100 читают spent=0, все проходят checkBudget, все резервируют и все уходят в Anthropic.
5. Повторяемо каждые сутки: период — календарный день UTC.
```

#### Ожидаемое / фактическое

- **Ожидается:** Не более 3 запросов в сутки на тарифе FREE; запрос сверх лимита получает 402 budget_exhausted ДО обращения к модели.
- **Фактически:** Проходит столько запросов, сколько их запущено параллельно. Перерасход ограничен только степенью параллелизма клиента.

#### Последствия

Прямой денежный ущерб владельцу ключа Anthropic: платит он, лимит не действует. ~33-кратное превышение при 100 потоках, повторяемо ежедневно и с любого числа бесплатных аккаунтов. Одновременно обесценивается платная подписка: тариф FREE даёт то, за что берут деньги.

#### Первопричина

Классический TOCTOU. Атомарный примитив написан правильно, но его результат отброшен на стыке слоёв.

#### Предлагаемое исправление

```
Вернуть итог из ai_usage_add и решать по нему, а не по прочитанному заранее:

// _shared.js
export async function recordSpend(userId, micro, period, { count = true } = {}) {
  const delta = Math.round(Number(micro) || 0)
  if (!delta) return { ok: true, total: null }
  const { data, error } = await admin().rpc('ai_usage_add', {...})
  if (error) { console.error(...); return { ok: false, total: null } }
  return { ok: true, total: Number(data) }      // ← итог больше не теряется
}

// chat.js / vision.js
const r = await reserve(user.id, reserved, period)
if (!r.ok) return res.status(503).json({ error: 'accounting_unavailable' })
const budget = budgetForTier(tier)
if (budget !== null && r.total > budget) {
  await settle(user.id, { reserved, actual: 0 }, period)   // вернуть резерв
  return budgetError(res, { reason: 'exhausted', remaining: 0 }, tier)
}

После этого решение принимается по значению, полученному ИЗ атомарной операции, и гонка закрывается без блокировок.
```

#### Тест против повторения

Тест на уровне api/ai: замокать ai_usage_add общим счётчиком, запустить N=50 обработчиков через Promise.all при бюджете на 3 запроса, проверить, что callClaude вызван не более 3 раз, а остальные получили 402.

### PRIV-001 — Anthropic, Stripe, Telegram и Open Food Facts не раскрыты ни в политике, ни в реестре обработки; политика опубликована как незаполненный шаблон

**P1** · CONFIRMED · уверенность HIGH · GDPR / раскрытие третьих лиц

- **Где:** `src/components/LegalSheet.jsx:38-110, docs/compliance/verzeichnis-verarbeitungstaetigkeiten.md, docs/compliance/avv-checkliste.md`
- **Затронутый поток:** Правовые документы ↔ фактическая обработка данных

#### Суть

Документы по защите данных описывают приложение, каким оно было до появления AI-ассистента, подписок и поддержки. Раздел «4. Empfänger / Auftragsverarbeiter» перечисляет Vercel, Supabase, Google и Reown/WalletConnect. Фактически данные уходят ещё четырём получателям, и ни один не назван:

• Anthropic PBC — получает профиль (пол, возраст, рост, вес, цели), дневник питания за сегодня, историю за несколько дней, «память» о пользователе и ФОТОГРАФИИ ЕДЫ. Это ровно те особые категории данных по ст. 9 GDPR, которые политика сама и называет особыми в разделе 2.
• Stripe — платёжные данные и email.
• Telegram — обращения в поддержку уходят в чат бота вместе с ником, именем и UUID пользователя.
• Open Food Facts (ru.openfoodfacts.org) — запросы уходят прямо из браузера, то есть третьей стороне видны IP пользователя и что он сканирует.

Отдельно: политика показывается людям с красной плашкой «⚠️ Шаблон. Проверьте у юриста и дополните своими данными», а вместо ответственного лица, адреса, контакта и надзорного органа стоят [Name], [Anschrift], [E-Mail], [zuständige Landesdatenschutzbehörde], «Stand: [Datum]».

#### Доказательство

```
grep по docs/compliance/*.md на «Anthropic», «Stripe», «Telegram», «AI», «Claude» — ноль совпадений во всех пяти документах.
LegalSheet.jsx:68 — список получателей: Vercel, Supabase, Google, Reown.
LegalSheet.jsx:41-43 — плашка «⚠️ Шаблон» в коде компонента, то есть видна в проде.
src/lib/aiPrompt.js:382-392 (buildUserContext) — состав того, что уходит модели.
api/ai/vision.js:60-66 — фотография уходит в Anthropic в теле запроса.
api/support.js:88-99 — ник, имя, UUID и текст уходят в Telegram.
src/lib/foods.js:1385, 1459 — прямой fetch на ru.openfoodfacts.org из браузера.
avv-checkliste.md — таблица AVV/DPA из 4 строк, все четыре чекбокса пусты (⬜).
```

#### Воспроизведение

```
1. Открыть приложение → Профиль → Правовая информация → Datenschutz.
2. Прочитать раздел 4 «Empfänger / Auftragsverarbeiter».
3. Сверить со списком реальных исходящих запросов в DevTools → Network при использовании AI-ассистента и сканера штрихкодов.
```

#### Ожидаемое / фактическое

- **Ожидается:** Все обработчики персональных данных перечислены в политике и в реестре по ст. 30; с каждым заключён договор по ст. 28; для передач в третьи страны указано основание.
- **Фактически:** Четыре обработчика не названы нигде, включая того, кто получает данные о здоровье и фотографии. Реестр по ст. 30 и чек-лист AVV не знают об AI, оплате и поддержке. Политика опубликована в виде шаблона с плейсхолдерами.

#### Последствия

Для приложения с немецкими правовыми текстами (то есть нацеленного на рынок ЕС), обрабатывающего данные по ст. 9, это нарушение ст. 13, 30 и, при отсутствии договоров, ст. 28 GDPR. Отсутствие названного ответственного лица и контакта делает невозможной реализацию прав субъекта — то самое, что проверяется в первую очередь по жалобе. Это блокирующий пункт для публичного запуска в ЕС, а не косметика.

#### Первопричина

Документы написаны один раз на раннем этапе и не обновлялись при добавлении AI, Stripe и Telegram. Ни одной автоматической связи между «появился новый исходящий запрос» и «дополнить реестр» нет.

#### Предлагаемое исправление

```
До запуска:
1. Дополнить LegalSheet → Datenschutz раздел 4: Anthropic PBC (США, SCC) — обработка данных о питании и фотографий для функции ассистента; Stripe Inc. (США) — платежи; Telegram (обращения в поддержку); Open Food Facts (запрос сведений о продукте по штрихкоду).
2. В разделе 2 добавить фотографии еды как отдельную категорию.
3. Дополнить verzeichnis-verarbeitungstaetigkeiten.md двумя новыми видами деятельности: «AI-ассистент» (ст. 9(2)(a), получатель Anthropic) и «Поддержка и модерация» (получатель Telegram), плюс «Оплата подписки» (Stripe).
4. Внести Anthropic, Stripe, Telegram в avv-checkliste.md и заключить DPA (у Anthropic и Stripe они стандартные, принимаются в кабинете).
5. Заполнить все [плейсхолдеры] и снять красную плашку «Шаблон» — пока она есть, документ юридически не является политикой.
6. Убедиться, что согласие на AI берётся отдельно: это передача данных ст. 9 новому получателю, и молчаливым оно быть не может.
```

#### Тест против повторения

Тест-сторож: список внешних хостов, к которым обращается код (fetch/axios/SDK), собирается grep-ом и сверяется со списком получателей в LegalSheet.jsx и в реестре. Новый хост без записи в обоих документах — падение теста. По образцу существующего sqlGuard.test.js.

### PRIV-002 — Загруженные изображения не удаляются никогда — в том числе при удалении поста и всего аккаунта; бакеты открыты на чтение

**P1** · CONFIRMED · уверенность HIGH · Право на удаление / хранилище

- **Где:** `src/lib/supabase.js:331-337 (deletePost), :322-330 (updatePost), :428-446 (uploadImage), src/lib/supabase.js deleteAccount, supabase/setup_all.sql:473-500, 2100-2128`
- **Затронутый поток:** Мысли с фото · фото в чате · удаление аккаунта

#### Суть

Ни один путь в приложении не удаляет объект из хранилища. `deletePost` стирает строку в таблице posts, `updatePost` заменяет ссылку на новую, `unsend_message` обнуляет image_url, `deleteAccount` удаляет посты, комментарии, реакции, app_state и самого пользователя — но сам файл в бакете во всех четырёх случаях остаётся.

Бакеты `post-images` и `chat-images` созданы с `public = true`, а политика чтения — `for select using (bucket_id = 'post-images')`, то есть без единого условия: файл доступен любому, включая неаутентифицированного, по прямой ссылке.

Автор осознанно выбрал модель «ссылка-пропуск» (путь содержит uuid v4, ~122 бита, не перебирается) и честно записал это в комментарии к миграции. Претензия не к выбору модели, а к тому, что у пропуска нет срока и его нельзя отозвать: ссылка, один раз попавшая к подписчику, переживает и отписку, и блокировку, и удаление поста, и удаление аккаунта.

#### Доказательство

```
supabase/setup_all.sql:479-481 — `create policy "chat-images read" … for select using (bucket_id = 'chat-images');` — предикат отсутствует.
supabase/setup_all.sql:2110-2111 — то же для post-images.
supabase/setup_all.sql:474, 2100 — `insert into storage.buckets (id, name, public) values (…, true)`.
src/lib/supabase.js:331 — тело deletePost целиком: один `.from('posts').delete().eq('id', postId)`, обращения к storage нет.
grep по src/ на `storage.from(...).remove(` — единственное совпадение отсутствует; `.remove(` встречается только как `classList.remove`.
deleteAccount — удаляет 6 таблиц, storage не трогает.
Для сравнения: бакет `dm-media` (setup_all.sql:12460) сделан правильно — `public = false`, чтение через `is_conversation_member`, клиент получает подписанную ссылку на час (src/lib/messaging.js:327).
```

#### Воспроизведение

```
1. Пользователь A публикует мысль с фотографией, видимость «только подписчикам».
2. Подписчик B открывает ленту, из DevTools копирует URL изображения.
3. A блокирует B, затем удаляет мысль, затем удаляет аккаунт целиком.
4. B (или кто угодно, кому B передал ссылку, в том числе без входа в приложение) открывает тот же URL — изображение отдаётся.
```

#### Ожидаемое / фактическое

- **Ожидается:** Удаление поста, отмена сообщения и удаление аккаунта делают изображение недоступным.
- **Фактически:** Изображение остаётся публично доступным бессрочно. Никакого способа его удалить у пользователя нет.

#### Последствия

Нарушение права на удаление (ст. 17 GDPR): после удаления аккаунта персональные данные — фотографии, в том числе с людьми и обстановкой, — продолжают отдаваться с сервера проекта. Дополнительно: фото из «закрытых» мыслей не защищены ничем, кроме неразглашения ссылки, и бесконечный рост платного хранилища.

#### Первопричина

Жизненный цикл файла не связан с жизненным циклом строки, которая на него ссылается. Бакет `dm-media` был позже сделан закрытым, но два ранних бакета остались публичными и без уборки.

#### Предлагаемое исправление

```
Короткий путь (снимает утечку после удаления):
1. Хранить в posts не публичный URL, а путь в бакете (`user_id/uuid.jpg`).
2. Удалять объект вместе со строкой. Надёжнее — триггером в базе через очередь на удаление, а не из клиента: клиент может закрыть вкладку между двумя вызовами.
3. В deleteAccount перед удалением аккаунта выгрузить список объектов пользователя (`storage.from(b).list(uid)`) и удалить их.

Правильный путь (снимает и бессрочный пропуск):
4. Перевести post-images и chat-images на модель dm-media: `public = false`, политика чтения через `can_view_post` / участие в диалоге, клиент получает подписанную ссылку. Тогда отписка и блокировка начинают действовать и на картинки.
Миграция существующих файлов: бакет переключается в private одной строкой, ссылки в старых постах переписываются на пути пакетным скриптом.
```

#### Тест против повторения

Интеграционный тест: создать пост с изображением → удалить пост → запросить URL изображения → ожидать 404/403. Аналогично для deleteAccount. Плюс сторож: политика чтения бакета без предиката — падение теста policy-audit.mjs.

### SEC-002 — Незаданная переменная цены превращает неизвестный прайс в высший тариф AI_PREMIUM

**P2** · CONFIRMED · уверенность HIGH · Подписки / повышение прав

- **Где:** `api/stripe/_shared.js:26-35 (TIER_BY_PRICE), api/stripe/webhook.js:46-48 (upsertSubscription)`
- **Затронутый поток:** Вебхук Stripe → тариф пользователя

#### Суть

Карта прайс-ID → тариф строится вычисляемыми ключами из переменных окружения. Если переменная не задана, ключом становится СТРОКА "undefined". В вебхуке тариф ищется как `TIER_BY_PRICE[priceId]`; когда priceId равен undefined, JavaScript приводит ключ к той же строке "undefined" — и находит запись.

Последняя запись в объекте — AI_PREMIUM. То есть при незаданной STRIPE_PRICE_AI_PREMIUM отказ определить цену подписки даёт не FREE, а САМЫЙ ВЫСОКИЙ тариф: безлимитный бюджет и модель Sonnet вместо Haiku. Отказоустойчивость направлена в сторону, противоположную безопасной.

STRIPE_PRICE_AI_PREMIUM не упомянута в .env.example (там задокументированы только STRIPE_PRICE_AI и STRIPE_PRICE_AI_PLUS), то есть в проде она с высокой вероятностью не задана.

#### Доказательство

```
Проверено запуском на реальной семантике JS:

  process.env.STRIPE_PRICE_AI = 'price_ai_123'
  process.env.STRIPE_PRICE_AI_PLUS = 'price_plus_456'
  delete process.env.STRIPE_PRICE_AI_PREMIUM
  TIER_BY_PRICE = { [env.AI]:'AI', [env.PLUS]:'AI_PLUS', [env.PREMIUM]:'AI_PREMIUM' }

  ключи карты: ["price_ai_123","price_plus_456","undefined"]
  TIER_BY_PRICE[undefined] → "AI_PREMIUM"
  mappedTier = TIER_BY_PRICE[undefined] || 'FREE' → "AI_PREMIUM"

.env.example: STRIPE_PRICE_AI и STRIPE_PRICE_AI_PLUS есть, STRIPE_PRICE_AI_PREMIUM отсутствует.
webhook.js:46 — `const priceId = subscription?.items?.data?.[0]?.price?.id` — цепочка опциональна, то есть undefined здесь штатно возможен.
```

#### Воспроизведение

```
Требуется событие подписки, у которого не читается items.data[0].price.id (подписка без элементов, отличие формы объекта между версиями API, частично развёрнутый объект в полезной нагрузке вебхука). Статус при этом должен быть живым (active/trialing/past_due).
Прямой проверки на боевом Stripe не проводилось — оценка сделана по коду, поэтому эксплуатируемость помечена как требующая подтверждения, а сам дефект подтверждён.
```

#### Ожидаемое / фактическое

- **Ожидается:** Не удалось определить тариф по цене → FREE.
- **Фактически:** Не удалось определить тариф по цене → AI_PREMIUM, безлимит.

#### Последствия

Бесплатная выдача высшего тарифа. В деньгах это безлимитный расход на Sonnet за счёт владельца. Эксплуатируемость зависит от формы события Stripe и оценивается как низкая, но цена ошибки высока, а исправление — одна строка.

#### Первопричина

Вычисляемые ключи объекта молча принимают undefined и приводят его к строке. Отсутствует явная проверка, что priceId вообще есть.

#### Предлагаемое исправление

```
Строить карту только из заданных переменных и требовать явного priceId:

export const TIER_BY_PRICE = Object.fromEntries(
  [[process.env.STRIPE_PRICE_AI, 'AI'],
   [process.env.STRIPE_PRICE_AI_PLUS, 'AI_PLUS'],
   [process.env.STRIPE_PRICE_AI_PREMIUM, 'AI_PREMIUM']]
  .filter(([id]) => typeof id === 'string' && id.length > 0)
)

// webhook.js
const priceId = subscription?.items?.data?.[0]?.price?.id
if (!priceId) console.error('[stripe/webhook] у подписки нет цены', subscription?.id)
const mappedTier = (priceId && TIER_BY_PRICE[priceId]) || 'FREE'

И дополнительно задокументировать STRIPE_PRICE_AI_PREMIUM в .env.example.
```

#### Тест против повторения

Юнит-тест рядом с origin.test.js: при незаданной STRIPE_PRICE_AI_PREMIUM карта не содержит ключа "undefined", а upsertSubscription с подпиской без price даёт tier === 'FREE'.

isAllowedOrigin — чистое сравнение строки со списком, никакой криптографии.
api/feedback.js:99 — `const ip = String(req.headers['x-forwarded-for'] || '').split(',')[0].trim()` — берётся ЛЕВЫЙ элемент, то есть та часть цепочки, которую клиент может задать сам.

api/feedback.js:5 — `const CHAT_IDS = [571138125, 938539456]` — адресаты заданы в коде.

```

  -H "X-Forwarded-For: 10.0.0.$((RANDOM%255))" \
  -d '{"text":"проверка"}'

Запустить в цикле с параллелизмом: каждый запрос со своим X-Forwarded-For попадает в отдельную корзину, а холодные экземпляры начинают счёт заново.
Проверка проводилась ТОЛЬКО чтением кода; по боевому адресу запросы не отправлялись.

#### Ожидаемое / фактическое

#### Последствия

Затопление личного чата владельца (и второго адресата) — вплоть до того, что настоящие обращения из поддержки в этом потоке теряются. Расход квоты Telegram Bot API и выполнения функций. Прямой утечки данных нет.

#### Первопричина

Заголовок Origin принят за границу доступа, а не за один из слоёв; ограничение частоты сделано на структуре, не переживающей архитектуру платформы.

#### Предлагаемое исправление

```
Кратко: либо потребовать вход, как в api/support.js, либо перенести лимит в общее хранилище.
1. Самое дешёвое и правильное: `const user = await getUserFromRequest(req); if (!user) return res.status(401)…` — «совет по приложению» вполне может требовать аккаунта, как и поддержка.

3. Ключ лимита брать не из левого элемента XFF, а из значения, которому можно верить на этой платформе.
4. Вынести CHAT_IDS в переменную окружения — TG_ADMIN_CHAT_IDS уже существует ради этого в api/telegram/_tg.js.
```

#### Тест против повторения

Тест: 10 последовательных вызовов обработчика с разными X-Forwarded-For при одном и том же аккаунте/адресе должны дать 429 начиная с четвёртого — сегодня дают 200.

### SEC-004 — Вебхук Stripe не защищён от переупорядоченной доставки: позднее старое событие воскрешает отменённый тариф

**P2** · PROBABLE · уверенность MEDIUM · Подписки / целостность состояния

- **Где:** `api/stripe/webhook.js:88-130, upsertSubscription:43-62`
- **Затронутый поток:** Жизненный цикл подписки

#### Суть

Каждое событие подписки делает безусловный upsert строки целиком. Ни `event.created`, ни `updated_at` строки в базе не сравниваются с тем, что уже записано. Stripe явно не гарантирует порядок доставки и повторяет неподтверждённые события.

Значит последовательность «updated (active) → deleted (canceled)», доставленная в обратном порядке или с повтором первого после второго, оставит в базе tier активного тарифа.

#### Доказательство

```
webhook.js:43-62 — upsertSubscription не читает текущую строку и не сравнивает временные метки.
Защита от повтора держится только на 5-минутном допуске подписи в constructEvent — он отсекает старый повтор, но не меняет порядок доставки внутри окна.
Проверка проводилась чтением кода; воспроизведение на боевом Stripe не выполнялось — отсюда статус PROBABLE.
```

#### Воспроизведение

```
Смоделировать двумя вызовами обработчика с корректной подписью: сначала событие customer.subscription.deleted (status canceled), затем customer.subscription.updated со СТАРЫМ event.created и status active. В базе останется живой тариф.
```

#### Ожидаемое / фактическое

- **Ожидается:** Событие, более старое, чем уже применённое к этой подписке, игнорируется.
- **Фактически:** Применяется последнее пришедшее, независимо от времени его создания.

#### Последствия

Продолжение платного доступа после отмены или неоплаты. Денежные потери ограничены, но восстановление состояния ручное. Обратный случай (отмена «затирает» продление) бьёт по платящему пользователю.

#### Первопричина

Отсутствует контроль версии/времени при записи — при том, что ровно такой контроль правильно сделан в соседней части проекта (save_app_state с compare-and-swap по revision).

#### Предлагаемое исправление

```
Добавить колонку и сравнение:

alter table public.subscriptions
  add column if not exists last_event_at timestamptz;

// webhook.js
await admin().from('subscriptions').upsert({ …, last_event_at: new Date(event.created * 1000).toISOString() })
  // и отбрасывать событие, если в строке уже стоит более поздний last_event_at

### UX-001 — Количество продукта не ограничено сверху: 999999999999 г принимаются и портят всю статистику

**P3** · CONFIRMED · уверенность HIGH · Целостность данных / ввод

```

  "999999999999" → "999999999999"  (Number: 999999999999)
  "-1"          → "1"              (минус снимается — отрицательных нет)

#### Воспроизведение

```

```

- **Ожидается:** Количество ограничено разумной верхней границей (например, 10 000 г / 100 порций), лишнее обрезается или поле не принимает ввод.
- **Фактически:** Принимается любое число; статистика портится до ручной правки.

#### Последствия

Не безопасность, а качество данных — но восстановление требует найти и удалить запись, а в статистике это выглядит как поломка приложения. Достижимо обычной опечаткой (залипшая клавиша, вставка из буфера), не только намеренно. Смягчение есть: запись удаляется, а день можно исключить из статистики.

#### Первопричина

Санитайзер отвечает за форму строки, а не за диапазон значения; диапазон не проверяет никто.

#### Предлагаемое исправление

```
Добавить границу в sanitizeAmount (одно место на все шесть полей):

export const MAX_AMOUNT = 100000   // 100 кг — заведомо выше любого реального приёма

export function sanitizeAmount(raw, max = MAX_AMOUNT) {
  const s = String(raw ?? '').replace(/[^\d.,]/g, '').replace(/,/g, '.')
  const dot = s.indexOf('.')
  const clean = dot === -1 ? s : s.slice(0, dot + 1) + s.slice(dot + 1).replace(/\./g, '')
  if (clean === '' || clean === '.') return clean
  const n = Number(clean)
  return Number.isFinite(n) && n > max ? String(max) : clean
}

Важно вернуть именно строку и сохранить «12.» (незаконченный ввод дробного) — на это уже есть тест в foodSearch.test.js:323.
```

#### Тест против повторения

Дополнить существующий тест foodSearch.test.js:317: sanitizeAmount('999999999999') === '100000', sanitizeAmount('12.') === '12.' (не сломать текущее поведение).

### SEC-005 — Блокировка не распространяется на общие групповые диалоги

**P3** · CONFIRMED · уверенность HIGH · Приватность / блокировка

- **Где:** `supabase/setup_all.sql — политики "messages select" и "messages insert" (последние редакции)`
- **Затронутый поток:** Блокировка · групповые диалоги

#### Суть

В личной переписке блокировка работает безупречно в обе стороны: отправка запрещена (`can_message` → `get_message_permission`), чтение отфильтровано (`not is_blocked_between(sender, auth.uid())`).

В групповом диалоге обе проверки не применяются. Фильтр чтения стоит под условием `recipient is null or not is_blocked_between(...)` — у группового сообщения recipient пуст, и условие выполняется тождественно. Отправка проверяет только участие в диалоге.

То есть если заблокировавший и заблокированный оказались в одной группе, заблокированный продолжает писать, а заблокировавший — читать.

#### Доказательство

```
Политика messages select (последняя редакция):
  (auth.uid() = sender or auth.uid() = recipient
   or (conversation_id is not null and is_conversation_member(conversation_id, auth.uid())))
  and (recipient is null or not is_blocked_between(sender, auth.uid()))
                ^^^^^^^^^^^^^^^^^^ для группы условие истинно всегда

Политика messages insert (последняя редакция):
  auth.uid() = sender and ((recipient is not null and can_message(sender, recipient))
                           or (conversation_id is not null and is_conversation_member(conversation_id, auth.uid())))
                                                               ^^^ блокировка не проверяется

Смягчающие обстоятельства подтверждены по коду: прямое затаскивание в группу закрыто — `can_invite_to_group` проверяет `is_blocked_between` (setup_all.sql), `create_group_conversation` проверяет отдельно ещё раз, а настройка group_invites по умолчанию 'following' (setup_all.sql:8259), то есть добавить в группу может только тот, на кого приглашаемый подписан.
```

#### Воспроизведение

```
1. A и B состоят в группе, созданной третьим человеком C.
2. A блокирует B.
3. B пишет в группу.
4. A видит сообщение B в общей ленте группы.
```

#### Ожидаемое / фактическое

- **Ожидается:** Решение «я не хочу видеть этого человека» действует всюду, где приложение показывает его сообщения.
- **Фактически:** В группах блокировка не действует ни на чтение, ни на отправку.

#### Последствия

Канал для преследования в обход блокировки. Практический риск существенно снижен тем, что попасть в общую группу с заблокировавшим непросто: нужен посредник, на которого жертва подписана. Поэтому P3, а не P2.

#### Первопричина

Групповые диалоги добавлены поздней миграцией (2026-09-09_conversations), и предикат блокировки, написанный для личной переписки, на новый случай распространён не был.

#### Предлагаемое исправление

```
Распространить проверку на оба направления:

-- чтение: скрывать сообщения заблокированных и в группах
and not public.is_blocked_between(sender, auth.uid())
   -- вместо (recipient is null or not …)

-- отправка: в группе тоже учитывать блокировку хотя бы попарно
… or (conversation_id is not null
      and public.is_conversation_member(conversation_id, auth.uid()))

Замечание по проектированию: полный запрет отправки в группу при блокировке хотя бы одним участником спорен (это наказывает остальных). Практичнее оставить отправку, но ГАРАНТИРОВАННО скрывать сообщения от того, кто заблокировал, — то есть поправить прежде всего политику чтения.
```

#### Тест против повторения

Тест SQL-уровня в supabase/verify_social_v2.sql: создать группу с A, B, C; A блокирует B; выборка messages от имени A не содержит сообщений B.

#### Доказательство

#### Ожидаемое / фактическое

- **Ожидается:** У каждого управляющего элемента есть доступное имя.
- **Фактически:** Десять кнопок безымянны для вспомогательных технологий.

#### Последствия

Экран добавления еды — основной сценарий приложения; для незрячего пользователя навигация по нему становится угадыванием. Правка тривиальна.

#### Первопричина

Символ в содержимом кнопки выглядит как текст и создаёт ложное ощущение, что имя есть.

#### Предлагаемое исправление

```
Добавить aria-label в перечисленные места:

```

Тест-сторож по образцу designGuard.test.js: разобрать JSX и падать, если найден <button>, у которого нет ни текстового содержимого длиннее одного символа, ни aria-label.

### SEC-006 — CSP разрешает unsafe-inline и unsafe-eval, connect-src открыт на любой https

**P3** · CONFIRMED · уверенность HIGH · Защита в глубину

#### Суть

```

- **Ожидается:** CSP служит вторым рубежом на случай, если XSS всё-таки появится.
- **Фактически:** При появлении XSS политика его не остановит, а connect-src не ограничит вывод данных.

#### Последствия

Сегодня эксплуатируемой уязвимости нет — это именно потеря защиты в глубину. Значение вырастет, как только в проекте появится сторонний виджет или отрисовка пользовательской разметки.

#### Первопричина

'unsafe-eval' обычно попадает в политику ради дев-режима или библиотеки; в данном случае, вероятно, ради Web3-стека (который выключен).

#### Предлагаемое исправление

```
Попробовать убрать 'unsafe-eval' и проверить, что сборка работает (Vite в проде eval не требует; требовал его, скорее всего, AppKit — а он выключен).
connect-src сузить до фактических адресатов:
  connect-src 'self' https://<project>.supabase.co wss://<project>.supabase.co https://ru.openfoodfacts.org https://api.anthropic.com;
(запросы к Anthropic идут с сервера, так что его в connect-src может и не потребоваться — проверить по факту).
'unsafe-inline' в script-src убирается сложнее (нужны хэши или nonce); при отсутствии инлайн-скриптов в index.html — попробовать снять и проверить.
```

#### Тест против повторения

Проверка после правки: открыть приложение, пройти вход, AI-ассистента и сканер штрихкодов, убедиться в отсутствии нарушений CSP в консоли.

### SEC-007 — Тип загружаемой в AI картинки проверяется только по заявленному media_type, без сигнатуры файла

**P3** · CONFIRMED · уверенность HIGH · Проверка входных данных

- **Где:** `api/ai/vision.js:19, 32-39`
- **Затронутый поток:** Распознавание еды по фото

#### Суть

Проверяется поле `image.media_type` из тела запроса и длина base64. Фактическое содержимое не проверяется: клиент может объявить image/jpeg и прислать что угодно.

#### Доказательство

```
vision.js:19 — `const ALLOWED_TYPES = ['image/jpeg', 'image/png', 'image/webp']`.
vision.js:33 — `if (!image?.data || !ALLOWED_TYPES.includes(image.media_type))` — сравнивается заявленный тип.
vision.js:36-38 — ограничение длины base64 (3,5 МБ) есть и посчитано правильно, с учётом раздувания base64 и потолка тела функции.
Существенное смягчение: изображение НИГДЕ не сохраняется и никому не отдаётся — уходит в Anthropic в теле запроса и живёт только в памяти (vision.js:8-10 и состав messages на :60-66). Значит классические последствия (хранимый XSS через SVG, подмена файла) недостижимы.
```

```

```

#### Ожидаемое / фактическое

- **Ожидается:** Несоответствие объявленного типа содержимому отклоняется до обращения к модели.
- **Фактически:** Отклоняет только Anthropic, уже после списания резерва.

#### Последствия

Низкий: платит бюджетом сам отправитель, хранения нет. Ценность правки — экономия вызова и более честная ошибка пользователю.

#### Первопричина

Проверка типа сделана по метаданным, а не по данным.

#### Предлагаемое исправление

```
Сверить первые байты base64 с сигнатурой:

const MAGIC = {
  'image/jpeg': [[0xFF, 0xD8, 0xFF]],
  'image/png':  [[0x89, 0x50, 0x4E, 0x47]],
  'image/webp': [[0x52, 0x49, 0x46, 0x46]],   // RIFF, далее WEBP на смещении 8
}
const head = Buffer.from(image.data.slice(0, 24), 'base64')
const ok = MAGIC[image.media_type].some((sig) => sig.every((b, i) => head[i] === b))
if (!ok) return res.status(400).json({ error: 'bad_image', message: 'Файл не похож на изображение.' })
```

#### Тест против повторения

Тест обработчика: media_type image/png с телом из произвольных байт — ожидать 400 и отсутствие вызова callClaude.

### UX-002 — Оптимистичные переключатели приватности могут рассинхронизироваться с сервером при быстром переключении и ошибке

**P3** · PROBABLE · уверенность MEDIUM · Согласованность состояния

- **Где:** `src/components/social/PrivacyHub.jsx:80-86 (patch)`
- **Затронутый поток:** Профиль → Приватность

#### Суть

Переключатель меняет состояние сразу и откатывает его при ошибке, запоминая предыдущее значение как `const prev = p`. Защиты от параллельных вызовов нет, а `prev` — значение из замыкания текущего рендера.

При двух быстрых переключениях подряд, если ПЕРВЫЙ запрос завершится ошибкой уже после того, как второй ушёл, откат вернёт состояние, предшествующее первому, и экран разойдётся с сервером до следующей загрузки.

#### Доказательство

```
PrivacyHub.jsx:80-86 — тело patch целиком; нет ни флага «запрос в полёте», ни отмены предыдущего, ни перечитывания с сервера после ошибки.
Компонент содержит 17 обработчиков и ни одного состояния busy/pending (сверено по всем компонентам: у PrivacyHub, ConversationInfo и RelationshipSheet асинхронные действия без таких состояний).
Статус PROBABLE: путь рассуждения проверен по коду, но сценарий требует ошибки сети в узком окне и на живом приложении не воспроизводился.
```

#### Воспроизведение

```
1. Профиль → Приватность.
2. В DevTools включить троттлинг и отключить сеть на секунду.
3. Дважды быстро переключить «Закрытый аккаунт».
4. Первый запрос падает, второй проходит — экран показывает исходное значение, сервер хранит второе.
```

#### Ожидаемое / фактическое

- **Ожидается:** Экран после любой последовательности переключений показывает то, что на сервере.
- **Фактически:** Возможно расхождение до перезагрузки раздела.

#### Последствия

Для настроек приватности цена расхождения выше обычной: человек видит «закрыто», а на сервере открыто (или наоборот) и принимает решение по неверной картинке. Именно об этом предупреждает комментарий в шапке самого файла — «тумблер, который визуально меняется, но ничего не закрывает, вреднее пустого места».

#### Первопричина

Оптимистичное обновление без защиты от наложения запросов.

#### Предлагаемое исправление

```
Перечитывать состояние с сервера после ошибки вместо отката к запомненному значению — это надёжнее любого сравнения меток:

const patch = async (next, fn) => {
  setP((cur) => ({ ...cur, ...next }))
  setErr(null)
  const res = await fn()
  if (res?.error) { setErr(res.error); await load() }   // ← источник истины у сервера
}

Дополнительно — блокировать повторное нажатие на время запроса.
```

#### Тест против повторения

Тест компонента: два последовательных patch, первый отклоняется с задержкой; после обоих состояние равно ответу load(), а не первому prev.

### UX-003 — Поиск по префиксу позволяет перебрать базу пользователей; ограничения частоты на поиск нет

**P3** · CONFIRMED · уверенность HIGH · Перечисление пользователей

- **Где:** `supabase/setup_all.sql — search_users (последняя редакция)`
- **Затронутый поток:** Поиск людей

#### Суть

`search_users` требует минимум два символа, ищет по префиксу ника и имени, отдаёт не более 30 записей и исключает заблокированных. Ограничения частоты у неё нет — ни в базе, ни на клиенте.

Перебором двухсимвольных префиксов (около 1 500 запросов на латиницу и кириллицу) выгружается до ~45 000 карточек: ник, отображаемое имя, аватар, признак закрытости.

```
Функция возвращает user_id, username, display_name, avatar_url, is_private.
Ограничения: `char_length(q.v) >= 2`, `limit least(greatest(coalesce(p_limit,20),1),30)`, исключение себя и заблокированных.
В проекте есть триггеры ограничения частоты на изменяющие действия (limit_follows — 200/час, limit_posts — 60/час, limit_unaccepted_messages — 5 на адресата и 20 новых собеседников в час), но на чтение и поиск таких ограничений нет.
Закрытость аккаунта от перечисления не защищает: is_private отдаётся как поле, а сама карточка возвращается независимо от него.
```

#### Воспроизведение

```
Перебрать p_query по всем двухбуквенным сочетаниям, вызывая RPC search_users с обычным аккаунтом.
```

#### Ожидаемое / фактическое

- **Ожидается:** Поиск служит поиском знакомых, а не выгрузкой базы.
- **Фактически:** Полная выгрузка публичных карточек достижима за несколько тысяч запросов.

#### Последствия

Своего рода плата за любой поиск людей — полностью закрыть, не сломав функцию, нельзя. Значение возрастает при росте базы: готовый список ников и аватаров — сырьё для рассылки и подбора целей. Приватные данные (дневник, записи, переписка) при этом не раскрываются: их закрывают отдельные предикаты, проверенные в этом аудите.

#### Первопричина

Ограничения частоты сделаны для изменяющих операций, чтение не покрыто.

#### Предлагаемое исправление

```
Добавить ограничение частоты на поиск — по образцу уже имеющихся триггеров, но для функции:
• таблица search_log (user_id, at) и проверка «не более N вызовов в минуту» внутри search_users;
• либо ограничение на уровне платформы (Vercel Firewall / Supabase rate limit) для этого RPC.
Разумный порог — 30–60 поисков в минуту: живому человеку хватает с запасом, перебор становится непрактичным.
```

### AI-001 — Границы медицинской безопасности заданы только промптом; серверной проверки ответа нет

**P3** · CONFIRMED · уверенность HIGH · Безопасность AI

- **Где:** `src/lib/aiPrompt.js:282-292 (ГРАНИЦЫ ТЕМЫ), :148-149 (тон savage)`
- **Затронутый поток:** AI-ассистент

#### Суть

Промпт содержит продуманные границы: не ставить диагнозы, не назначать и не отменять лекарства, осторожность при беременности, диабете, болезнях ЖКТ/почек/печени, приёме препаратов, возрасте до 16, весе сильно ниже нормы и признаках расстройства пищевого поведения; прямой запрет предлагать дефицит ниже 1200 ккал женщинам и 1500 мужчинам и голодание дольше суток. Тон «без цензуры» отдельно инструктирован мгновенно и без мата переходить на спокойный регистр при признаках расстройства пищевого поведения, срыва, самоповреждения или тревоги.

Это заметно лучше, чем принято в приложениях такого рода. Но все перечисленные границы — инструкции модели, то есть мягкие. Серверной проверки ответа нет: ни фильтра, ни перепроверки числовых рекомендаций, ни заготовленного ответа с контактами помощи на случай, когда разговор уходит в тему самоповреждения.

#### Доказательство

```
aiPrompt.js:288-291 — текст границ.
api/ai/chat.js и vision.js — после parseReply ответ уходит пользователю без содержательных проверок: разбирается формат (parseReply в _shared.js), проверяется обрезанность, но не содержание.
Положительно: тариф и модель берутся из базы (tierOf), а не из тела запроса, — подмена тарифа через клиент невозможна (проверено).
Прямой цели «продукт даёт вредный совет» в этом аудите не ставилось: проверка требует прогонов на живой модели, которых не проводилось.
```

#### Воспроизведение

```
Требуется живой прогон с попытками обойти инструкции промпта; в рамках этого аудита не выполнялся.
```

#### Ожидаемое / фактическое

- **Ожидается:** Ответы, выходящие за медицинские границы, не доходят до пользователя вне зависимости от того, удалось ли обойти инструкции.
- **Фактически:** Единственный рубеж — следование модели инструкции.

#### Последствия

Приложение работает с питанием и весом, то есть с областью, где неудачный совет достигает уязвимой аудитории. Промпт написан ответственно и снижает риск, но один рубеж для такой темы — мало.

#### Первопричина

Безопасность реализована на уровне формулировок, а не архитектуры.

#### Предлагаемое исправление

```
Добавить второй рубеж на сервере, дёшево и без второй модели:
1. Проверка чисел в ответе: если в cards или reply предлагается суточная норма ниже порога из промпта — заменять на безопасный текст.
2. Список признаков кризисной темы (самоповреждение, суицид, полный отказ от еды) в ВОПРОСЕ пользователя: при совпадении отвечать заготовленным текстом с контактами помощи, не обращаясь к модели вовсе. Так делают потому, что именно на этих запросах поведение модели наименее предсказуемо, а цена ошибки наибольшая.
3. Зафиксировать в правовых текстах, что ассистент не является медицинской консультацией (сейчас этого нет ни в AGB, ни в Datenschutz).
```

#### Тест против повторения

Тест на серверную проверку: ответ модели с рекомендацией 900 ккал в сутки обязан быть заменён; вопрос из кризисного списка обязан не доходить до callClaude.

### PERF-001 — Главный чанк 1,15 МБ (341 КБ в gzip); разбиение на части не настроено

**P4** · CONFIRMED · уверенность HIGH · Производительность

- **Где:** `vite.config.js, результат npm run build`
- **Затронутый поток:** Первая загрузка

#### Суть

Сборка предупреждает о чанках больше 500 КБ. Крупнейший загружаемый — index-DnFkNcWe.js, 1 149 КБ (341 КБ gzip). Второй — 642 КБ (175 КБ gzip). manualChunks в vite.config.js не настроен; конфигурация минимальна и содержит только плагин React и подстановку версии.

Отдельно отмечу: ленивые границы в проекте есть и сделаны осознанно (lazyWithReload, LazyBoundary, вынос Web3 и тяжёлых экранов в отдельные чанки) — то есть проблема не в отсутствии подхода, а в том, что основной чанк не разделён.

#### Доказательство

```
npm run build:
  dist/assets/index-DnFkNcWe.js     1 149,49 kB │ gzip: 341,31 kB
  dist/assets/index-AGvWEndH.js       642,35 kB │ gzip: 174,99 kB
  dist/assets/Web3Button-…js        2 682,65 kB │ gzip: 773,83 kB  (не загружается, см. DEP-001)
  предупреждение rollup о чанках > 500 kB.
src/lib/foods.js — 1 496 строк справочника продуктов; src/components/AddMealSheet.jsx — 2 267 строк.
```

#### Воспроизведение

```

```

#### Ожидаемое / фактическое

- **Ожидается:** Первый экран загружается, не дожидаясь справочника продуктов и экрана добавления еды.
- **Фактически:** Основной чанк включает всё сразу.

#### Последствия

На медленной мобильной сети — ощутимая задержка первого показа. Смягчено service worker-ом, который кэширует ядро после первого визита, поэтому страдает только первое открытие.

#### Первопричина

manualChunks не настроен; крупный справочник продуктов и самый большой экран попадают в основной чанк.

#### Предлагаемое исправление

```
Вынести справочник и тяжёлые экраны:

// vite.config.js
build: {
  rollupOptions: {
    output: {
      manualChunks: {
        supabase: ['@supabase/supabase-js'],
        foods: ['./src/lib/foods.js', './src/lib/foodMicros.js'],
      },
    },
  },
}

Плюс ленивая загрузка AddMealSheet (2 267 строк, открывается по кнопке, а не на первом экране) — в проекте уже есть lazyWithReload ровно для этого.
```

#### Тест против повторения

Проверка после правки: ни один загружаемый при старте чанк не превышает 500 КБ.

## Можно ли выпускать сегодня?

**НЕТ — не для широкой публики в ЕС.** Для закрытого теста на ограниченном круге согласившихся пользователей — да.

- Политика конфиденциальности показывается людям как незаполненный шаблон: вместо имени и адреса ответственного — `[Name]` и `[Anschrift]`, сверху красная плашка «Проверьте у юриста».
- Приложение отправляет данные о здоровье и фотографии еды в Anthropic и нигде об этом не сообщает.
- Stripe и Telegram тоже получают персональные данные и тоже не названы.
- Удаление аккаунта не удаляет загруженные фотографии — они остаются публично доступными навсегда.
- Любой пользователь обходит дневной лимит AI параллельными запросами и тратит деньги владельца.
- `/api/feedback` открыт без входа: личный Telegram владельца затапливается одной командой curl.
- На ветке красный тест и расхождение `setup_all.sql` с миграциями.

**Почему это хорошая новость:** ни одна из проблем не архитектурная. Переписывать ничего не нужно — 14 из 22 находок закрываются правкой в несколько строк, а самая тяжёлая занимает один-два дня. Фундамент проверку выдержал: модель прав выстроена верно, подмены личности нет нигде, синхронизация сделана на уровне, который редко встречается и в коммерческих продуктах.
