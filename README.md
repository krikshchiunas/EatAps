# EatAps

Персональная система управления питанием (PWA). React + Vite, local-first, синхронизация через Supabase.

## Запуск локально

```bash
npm install
npm run dev
```

Без ключей Supabase приложение работает офлайн (данные только на устройстве). Чтобы включить аккаунты и синхронизацию — см. ниже.

### Проверки перед отправкой изменений

```bash
npm run verify
```

Это `lint` → тесты → проверки SQL → продакшен-сборка: ровно то же, что гоняет
CI на каждый пулл-реквест (`.github/workflows/ci.yml`). По отдельности:

| Команда | Что делает |
|---|---|
| `npm run lint` | ESLint, настроенный на **баги, а не на стиль**: условные хуки, опечатки в именах, устаревшие зависимости эффектов |
| `npm test` | 883 теста, включая сторожей заголовков, SQL, лимитов AI и вебхука Stripe |
| `npm run sql:verify` | сверяет `setup_all.sql` с миграциями, проверяет идемпотентность и каталог схемы |
| `npm run build` | продакшен-сборка |

Версия Node закреплена в `.nvmrc` (24). Минимум — 20.11 (`engines` в `package.json`).

## Подключение Supabase (аккаунты + облако)

1. Создайте проект на https://supabase.com
2. **SQL Editor** → вставьте содержимое
   [`supabase/setup_all.sql`](supabase/setup_all.sql) целиком → **Run**.
   Это все миграции, склеенные в правильном порядке; одного прогона достаточно
   и для новой базы, и для существующей с данными — файл идемпотентен целиком.

   > ⚠️ Отдельные файлы из `supabase/migrations/` вне порядка прогонять нельзя,
   > а всё, что лежит в `supabase/archive/`, — нельзя вообще
   > ([почему](supabase/archive/README.md)).
   >
   > Что в базе на самом деле — [`supabase/docs/catalog.md`](supabase/docs/catalog.md).
   > Как она устроена и как её менять — [`supabase/docs/`](supabase/docs/README.md).

3. Разбор миграций ниже нужен, только если обновляете базу пошагово. При
   установке через `setup_all.sql` шаг 2 их уже включает. Короткая карта всех
   миграций — [`supabase/docs/04-history.md`](supabase/docs/04-history.md).
   - [`migrations/2026-08-06_account_sync.sql`](supabase/migrations/2026-08-06_account_sync.sql) —
     версионирование состояния (`revision` + запись только через `save_app_state`),
     `presence` вместо `app_state.last_seen`, Realtime для `app_state`. Без него
     правки, сделанные на двух устройствах одновременно, затирают друг друга.
   - [`migrations/2026-08-07_friend_privacy.sql`](supabase/migrations/2026-08-07_friend_privacy.sql) —
     друг получает только то, что показано на экране (имя, фото, био, любимые
     места, норма калорий, дневник), а не всю строку состояния с весом, ростом
     и возрастом. Плюс самолечение публичного ID (сам ID удалён миграцией от
     2026-08-26).

     после смены политики покажет карточку друга пустой.
   - [`migrations/2026-08-08_hardening.sql`](supabase/migrations/2026-08-08_hardening.sql) —
     устранение слабостей аудита: имя в заявке в друзья ставит сервер (его
     нельзя подделать), ограничения на размер состояния, на размер и тип
     загружаемых фото, на частоту заявок в друзья.
   - [`migrations/2026-08-08_chat_reactions.sql`](supabase/migrations/2026-08-08_chat_reactions.sql) —
     реакция на сообщение в чате (двойной тап → 🥕). Переключение делает
     сервер (RPC `toggle_message_reaction`), получателю разрешено менять
     только собственный ключ реакции — даже прямой запрос в обход RPC не
     допишет реакцию под чужим именем.
   - [`migrations/2026-08-09_unpredictable_public_id.sql`](supabase/migrations/2026-08-09_unpredictable_public_id.sql) —
     публичный ID для добавления в друзья стал случайным (12 символов вместо
     последовательных `AA000001`). Раньше перебор от `AA000001` находил всех
     зарегистрированных пользователей.
     **Устарело:** публичных ID больше нет, их удаляет миграция от 2026-08-26.
     Этот файл нужен только при установке с нуля по порядку и **не должен
     прогоняться отдельно после неё** — он пишет в колонку, которой уже нет.
   - [`migrations/2026-08-11_profile_and_thoughts.sql`](supabase/migrations/2026-08-11_profile_and_thoughts.sql) —
     профиль стал публичной витриной. Друг видел списки «да в еде» и «нет в еде»
     (`friend_state` отдавал `noGos`/`toGos` рядом с `bio`; списки удалены
     миграцией от 2026-08-28), появился раздел
     «Мои мысли»: таблицы `posts`, `post_reactions`, `post_comments` со своими
     RLS, RPC `toggle_post_reaction` (реакция ставится по `auth.uid()`, а не по
     присланному id) и `list_posts` (наружу уходят только счётчики реакций —
     поимённый список отреагировавших остаётся на сервере), плюс бакет
     `post-images` с ограничением размера и типа файла.
     ⚠️ С 2026-09-12 этот бакет **закрыт**: см. раздел «Вложения приватны» ниже.
     **Порядок:** не важен. Без миграции новый фронтенд покажет «Раздел пока
     недоступен» вместо мыслей и не отобразит списки у друга; ничего не ломается.
   - [`migrations/2026-08-25_social_graph.sql`](supabase/migrations/2026-08-25_social_graph.sql) —
     социальный граф: подписки (`follows`), блокировки (`blocks`), серверные
     уведомления (`notifications`), видимость постов (`posts.visibility`),
     публичные профили с `username`, поиск людей и лента (`list_feed`).
     Разделяет то, что раньше было одним понятием: **подписка ≠ дружба ≠
     доступ**. Дружба по-прежнему даёт самое широкое право (дневник питания и
     личные сообщения), подписка — только контент, помеченный автором как
     `public`/`followers`.

     **⚠️ Эта миграция МЕНЯЕТ МОДЕЛЬ ПРИВАТНОСТИ, и обратной дороги нет:**
     - имя, аватар и `username` становятся видны **любому** авторизованному
       пользователю, и все существующие аккаунты попадают в поиск по имени;
     - существующие «Мысли» переводятся из «только друзьям» в «подписчикам».

     Оба пункта расширяют аудиторию уже созданных данных. Перед прогоном на
     продакшене обновите [`docs/compliance`](docs/compliance/) (Verzeichnis von
     Verarbeitungstätigkeiten) и уведомьте пользователей — задним числом это
     не исправить.

     Что миграция намеренно НЕ делает: не открывает дневник питания
     подписчикам, не отдаёт `public_id` в публичном профиле и не разрешает
     писать в личку тем, кто не в друзьях.

     **Порядок:** сначала миграция, потом деплой фронтенда. Наоборот тоже не
     ломается — новый фронтенд без миграции покажет «Раздел пока недоступен»
     вместо ленты и событий.
   - [`migrations/2026-08-26_nickname_identity.sql`](supabase/migrations/2026-08-26_nickname_identity.sql) —
     ник вместо публичного ID и дружба вместо заявок.

     **Публичный ID удаляется целиком** — колонка `profiles.public_id` и все
     четыре функции вокруг неё. Единственный адрес человека — ник
     (`profiles.username`): уникальный, редактируемый в «Профиль →
     Редактировать профиль», и **поиск ищет только по нему**, не по
     отображаемому имени. Ранее розданные коды перестают работать.

     **Заявки в друзья исчезают как класс.** Друзья — это те, кто подписан друг
     на друга. Таблица `friendships` остаётся, но становится производной: её
     пишет триггер на `follows`, а клиентские INSERT/UPDATE/DELETE закрыты
     (иначе можно было бы выписать себе право переписки). Принятые дружбы
     переносятся в две подписки и остаются дружбами; незакрытые заявки
     превращаются в одностороннюю подписку заявителя.

     **⚠️ Последствие для приватности:** дневник питания и личные сообщения
     по-прежнему открыты только друзьям, но стать другом теперь можно нажатием
     «Подписаться в ответ» — без осознанного подтверждения заявки. Круг
     доступа к дневнику расширяется. Обновите [`docs/compliance`](docs/compliance/)
     перед прогоном на продакшене.

     **Порядок:** сначала миграция, потом деплой фронтенда. Старый фронтенд
     после неё покажет ошибку на кнопке «＋ По ID» и на заявках — ни того, ни
     другого в базе уже не будет.
   - [`migrations/2026-08-28_profile_rework.sql`](supabase/migrations/2026-08-28_profile_rework.sql) —
     переработка профиля. `friend_state` отдаёт из профиля только то, что
     рисует вкладка «О себе»: имя, аватар, `bio`, `guiltyPleasure` и норму
     калорий. Любимое блюдо, любимый ресторан и списки `noGos`/`toGos` («да в
     еде» / «нет в еде») удалены из приложения — заполнить их больше нечем,
     показывать негде, и база перестаёт их возить.

     Строки `app_state` не переписываются: у давних аккаунтов старые ключи
     остаются в блобе до первого сохранения профиля (клиент затирает их сам), а
     до тех пор их отбрасывает `friendView.js`.

     **Порядок:** не важен. Старый фронтенд с новой базой не найдёт удалённых
     полей и не покажет соответствующие строки — так же, как для незаполненного
     профиля; новый фронтенд со старой базой отбросит лишние ключи сам.
   - [`migrations/2026-09-05_social_hardening.sql`](supabase/migrations/2026-09-05_social_hardening.sql) —
     укрепление социальной системы. **Эту миграцию нужно прогнать обязательно:
     она чинит два отказа, которые ломают базу молча.**

     **Смена ника и сохранение состояния падали.** `guard_profile_update`
     продолжал читать `new.public_id` после того, как колонку удалила миграция
     2026-08-26: PL/pgSQL разрешает поля записи во время выполнения, поэтому
     файл прогонялся без жалоб, а падал КАЖДЫЙ `update` по `profiles` с 42703.
     Задевало это тех, кто завёл аккаунт после той миграции или менял имя либо
     фото, — то есть каждого нового человека.

     **Публичная витрина не обновлялась.** Тот же триггер откатывал
     `display_name` и `avatar_url` у любой записи с непустым `auth.uid()` —
     включая законную, из зеркалирующего триггера `app_state`. У новых
     аккаунтов имя и аватар оставались пустыми, и лента, поиск и списки людей
     показывали «Без имени» с буквой вместо фотографии. Миграция различает
     доверенную запись явным признаком и разово восстанавливает витрину.

     **Дружба могла не возникнуть.** Строку `friendships` писал триггер по
     встречной подписке, а две одновременные подписки друг на друга не видят
     строк друг друга (READ COMMITTED) — и не создавали дружбу ни одна.
     Пара оказывалась в состоянии «переписываться можно, дневник не виден, в
     списке друзей друг друга нет». Теперь пара сериализуется advisory-локом
     ДО вставки, а права считаются по подпискам (`is_friend_with`), а не по
     материализованной строке: политика дневника, списки и счётчики переехали
     на граф.

     **Блокировка обходилась через списки.** `list_followers`/`list_following`
     прятали отдельных заблокированных, но не проверяли право смотреть на сам
     профиль: заблокировавшего меня человека я по-прежнему мог перечислить
     прямым вызовом RPC. Ответы заблокированных под общим постом тоже были
     видны.

     **Переписка.** У сообщений появился `client_id` — ключ идемпотентности:
     повтор после обрыва сети больше не создаёт второе сообщение. Отправка
     идёт через `send_message` (отправитель — `auth.uid()`, а не поле запроса),
     история читается страницами через `list_messages` (прежний клиентский
     запрос брал САМЫЕ СТАРЫЕ 300 сообщений, то есть в длинной переписке не
     показывал ни одного свежего), список диалогов — через `list_conversations`
     вместо выгрузки двухсот сообщений на клиент.

     Плюс: пакетный `relationships_with` вместо N запросов на список людей,
     ограничение частоты реакций и смены ника, чистка уведомлений при удалении
     поста и ответа, индексы под лимиты частоты, снят бесполезный индекс по
     `visibility`.

     **Порядок:** сначала миграция, потом деплой фронтенда. Новый фронтенд со
     старой базой работает — он видит отсутствие функций и уходит на прежние
     пути (`legacySendChatMessage`, `legacyListMessagesWith`), но без
     идемпотентности и пагинации.

   - [`migrations/2026-09-07_open_messaging_and_diary_privacy.sql`](supabase/migrations/2026-09-07_open_messaging_and_diary_privacy.sql) —
     переписка открывается всем, дневник получает собственную настройку
     (`public` / `followers` / `mutuals` / `private`). Взаимная подписка
     перестаёт быть правом: она больше не открывает ни чат, ни дневник.
     Первое сообщение от того, на кого получатель не подписан, попадает в
     «Запросы»; вводятся квоты (5 сообщений до ответа, 20 новых собеседников
     в час) — раньше барьером от спама служила сама дружба.

   - [`migrations/2026-09-08_notification_upsert_fix.sql`](supabase/migrations/2026-09-08_notification_upsert_fix.sql) —
     второе сообщение человеку не отправлялось: upsert уведомления упирался в
     собственный guard-триггер, и исключение уносило всю транзакцию вместе с
     сообщением. Ломалось выборочно — только к тем, кто давно не заходил.

   - [`migrations/2026-09-09_social_graph_v2.sql`](supabase/migrations/2026-09-09_social_graph_v2.sql) —
     **закрытые аккаунты и всё, что из них следует.** Появляются
     `follow_requests` (просьба о подписке: до одобрения подписки НЕТ и прав
     она не даёт), `close_friends` (односторонний приватный круг),
     `restricted_users` (тихое ограничение), `user_mutes` (личное скрытие),
     `diary_access` (поимённый доступ к дневнику). Права на переписку
     становятся трёхзначными и настраиваются по трём категориям людей.
     Перечисления `post_visibility`, `diary_audience` и `notification_type`
     переводятся в `text` + `CHECK`: `alter type … add value` не переживает
     прогон `setup_all.sql` одной транзакцией.

     **Что происходит с данными:** ни один аккаунт не закрывается, ни одна
     подписка не теряется, круг дневника у всех остаётся прежним, права на
     переписку по умолчанию воспроизводят поведение до миграции. Никто не
     получает доступа, которого у него не было.

   - [`migrations/2026-09-09_conversations.sql`](supabase/migrations/2026-09-09_conversations.sql) —
     **переписка переезжает на диалоги.** Модель «у сообщения ровно один
     получатель» описывает разговор двоих и ничего кроме: групповой чат в неё
     не ложится никак. Появляются `conversations` и `conversation_members`;
     существующая переписка переносится автоматически (диалог на каждую пару,
     `conversation_id` у каждого сообщения, оба участника с уже принятыми
     решениями). Колонка `recipient` остаётся заполненной у личных сообщений —
     на ней держится совместимость со старым клиентом.

     Плюс: отзыв сообщения у всех, скрытие у себя (`message_deletions`,
     переживает смену устройства), прочтение указателем `last_read_at` вместо
     UPDATE на каждое сообщение, реакции произвольным эмодзи, архив, очистка
     переписки у себя, пересылка, поиск по сообщениям и ЗАКРЫТЫЙ бакет
     `dm-media` для вложений.

     **Порядок:** сначала обе миграции 2026-09-09 (в этом порядке), потом
     деплой фронтенда.
   **Одним файлом (основной путь).**
   [`supabase/setup_all.sql`](supabase/setup_all.sql) — все миграции, склеенные
   в правильном порядке, начиная с `migrations/2026-08-05_initial.sql`. Файл
   идемпотентен целиком и годится и для новой базы, и для существующей
   с данными.

   **Файл собирается скриптом, а не руками:**
   ```
   node scripts/build-setup-all.mjs
   ```
   Так было не всегда, и ручная склейка успела разъехаться: тело
   `sync_friendship_from_follows()` оказалось внутри `admin_subscriptions_apply()`,
   тело `issue_promo()` — внутри `sync_friendship_from_follows()`, а хвост
   `admin_subscriptions_apply()` повис после конца файла голым `insert`. То
   есть файл «полной установки» не выполнялся вовсе, и поднять базу с нуля по
   нему было нельзя. Порядок теперь задан одним списком в скрипте, а
   `npm test` проверяет, что копия не разошлась с источниками.

   ⚠️ **Автоматические проверки НЕ доказывают изоляцию.** Они выполняются от
   `service_role`, для которого RLS не применяется, и доказывают только, что
   правила существуют и что данные им не противоречат. Настоящая проверка —
   ручная матрица в конце `verify_social_v2.sql`, `verify_messaging.sql` и
   `verify_privacy.sql`: её прогоняют ТРЕМЯ реальными аккаунтами из
   пользовательских сессий.

   Как устроена социальная система целиком — в
   [`docs/social-system.md`](docs/social-system.md): модель данных, матрица
   приватности, жизненный цикл просьбы и запроса на переписку, семантика
   блокировки, ограничения и заглушения.
5. **Project Settings → API** → скопируйте `Project URL` и `anon public` ключ.
6. Локально: создайте `.env.local` (см. `.env.example`):
   ```
   VITE_SUPABASE_URL=https://xxxx.supabase.co
   VITE_SUPABASE_ANON_KEY=eyJ...
   ```
7. `npm run dev` — в разделе «Профиль» появится вход.

## Вложения приватны

С 12.09.2026 бакеты `chat-images` и `post-images` **закрыты**. До этого политика
чтения выглядела так:

```sql
create policy "chat-images read" on storage.objects
  for select using (bucket_id = 'chat-images');
```

Предиката нет вовсе: файл отдавался кому угодно, включая невошедшего, по прямой
ссылке. Защитой служила только неугадываемость адреса. Это «ссылка-пропуск»: она
не отзывается никогда — один раз показанное подписчику фото оставалось доступным
ему и после отписки, и после блокировки, и после удаления записи, и после
удаления всего аккаунта.

### Как устроено сейчас

**Инвариант.** Вложение переписки может прочитать только участник того
сообщения, к которому оно прикреплено. Изображение записи — только тот, кому
видна сама запись. Обе проверки выполняет база, а не интерфейс.

| Бакет | Публичный | Кто читает | Чем проверяется |
|---|---|---|---|
| `dm-media` | нет | участники диалога | первый сегмент пути — id диалога, `is_conversation_member` |
| `chat-images` | нет | участники сообщения | `can_read_chat_image(name)` по `messages.image_path` |
| `post-images` | нет | кому видна запись | `can_read_post_image(name)` через `can_view_post` |

**Новые вложения переписки** (включая обычные фото) уходят только в `dm-media`.
`chat-images` остался для чтения старой истории.

**Как файл связан с сообщением.** В строке хранится полный адрес, а политике
нужен путь внутри бакета. Вытаскивать его подстрокой прямо в политике нельзя —
это `LIKE` с ведущим шаблоном и полный проход по `messages` на каждое чтение.
Поэтому заведена **вычисляемая** колонка `image_path`: она заполняется сама и
для старых строк, и для будущих, не может разъехаться с адресом и
индексируется.

**Клиент** получает подписанную ссылку на час (`src/lib/storageUrl.js`,
`src/components/PrivateImage.jsx`). Постоянного публичного адреса у вложения
больше нет.

**Уборка.** Триггеры складывают пути осиротевших файлов в
`storage_cleanup_queue`; ежедневная `/api/maintenance` их удаляет. До этого
объект не удалялся **никогда** — ни при удалении записи, ни при удалении
аккаунта.

### Порядок выкатки

**Сначала фронтенд, потом миграция.** Новый клиент работает и с открытым, и с
закрытым бакетом: подписанная ссылка на публичный объект тоже валидна. Обратный
порядок оставит старые фотографии недоступными до выкатки фронтенда.

После миграции выполните [`verify_media_privacy.sql`](supabase/verify_media_privacy.sql) —
все строки должны быть `✔`.

## Регулярная уборка

`/api/maintenance` вызывается планировщиком Vercel раз в сутки (`crons` в
`vercel.json`) и делает две вещи, которые нельзя доделать внутри
пользовательского запроса:

* удаляет из хранилища файлы, оставшиеся без владеющей строки;
* возвращает зависшие резервы AI (`ai_reconcile`) — если функция не дожила до
  расчёта, списанный резерв остаётся на человеке.

Требует `CRON_SECRET`. **Без него точка отключена целиком** — открытая уборка
хуже неработающей. Ручной запуск:

```bash
curl -X POST https://www.eataps.com/api/maintenance -H "x-maintenance-token: $CRON_SECRET"
```

## Телеграм-бот модерации

Обращения из «Поддержки» падают в Телеграм, и под каждым есть кнопки бана. Чтобы
это заработало, нужны три переменные и один разовый вызов Телеграма:

| Переменная | Откуда берётся |
|---|---|
| `TG_TOKEN` | @BotFather → `/mybots` → бот → **API Token** |
| `TG_WEBHOOK_SECRET` | **вы придумываете сами** (см. ниже) |
| `TG_ADMIN_CHAT_IDS` | ваши chat id через запятую (узнать: напишите боту @userinfobot) |

`TG_WEBHOOK_SECRET` нигде не «находится». Адрес вебхука публичный, поэтому чужой
POST должен отсекаться: вы придумываете пароль, кладёте его в окружение и
сообщаете Телеграму. Дальше Телеграм присылает его в заголовке
`X-Telegram-Bot-Api-Secret-Token` на каждом обновлении, а
[`api/telegram/webhook.js`](api/telegram/webhook.js) сверяет. Пока переменной
нет, вебхук намеренно отвечает **503**: открытый эндпоинт модерации хуже
нерабочего.

Секрет нужно знать обеим сторонам, а в Vercel он хранится как sensitive и назад
не читается — поэтому настраивать обе стороны нужно за один проход. Это и делает
скрипт: придумает секрет, положит в Vercel, пересоберёт **последний уже выложенный**
прод-деплой (ваша рабочая копия в прод не уедет) и зарегистрирует вебхук:

```bash
bash scripts/setup-telegram.sh
```

Проверить, что получилось: `curl -X POST https://www.eataps.com/api/telegram/webhook`
должен вернуть **403** (секрет есть, но в запросе он не тот). **503** значит, что
переменная ещё не доехала до прода — нужен передеплой.

### Управление доступом

Отдельной админ-панели в приложении нет — администрирование идёт через
**SQL Editor**, как и баны. Два представления дают всю картину.

**Кто каким доступом обладает.** Одна строка на пользователя: действующий тариф,
откуда он взялся (оплата или промокод), до какого числа и сколько человек
потратил на ассистента в этом месяце.

```sql
select email, tier, source, until, ai_spent_usd, ai_requests
from public.admin_subscriptions
where tier <> 'FREE'
order by until;
```

Убрать `where` — увидите вообще всех, включая бесплатных. Полезные срезы:

```sql
-- заканчивается на этой неделе
select email, tier, source, until from public.admin_subscriptions
where until between now() and now() + interval '7 days' order by until;

-- кто больше всех тратит на ассистента в этом месяце
select email, tier, ai_spent_usd, ai_requests from public.admin_subscriptions
order by ai_spent_usd desc limit 20;

-- отменили подписку, но доступ ещё оплачен
select email, stripe_until from public.admin_subscriptions where cancel_at_period_end;
```

**Как расходятся коды.**

```sql
select code, tier, days, used, max_uses, left_uses, state, active_now, note
from public.admin_promo_codes order by created_at desc;
```

`state` — `active` / `used_up` / `expired`, `active_now` — сколько человек
пользуются доступом по этому коду прямо сейчас. В колонке `source` таблицы
доступа: `stripe`, `promo` или `none`.

Значения латиницей намеренно: кириллица в данных проходит через буфер обмена,
редактор и консоль, и на любом стыке может побиться — в таблице появятся
кракозябры вместо слов.

⚠️ Оба представления читают почты пользователей и закрыты от приложения:
права есть только у владельца базы и сервера. Проверка №84 в `verify.sql`
следит, чтобы их случайно не открыли.

### Промокоды

Код даёт тариф на срок, без Stripe и без списания денег.

**Выпустить код** — одна команда, код придумывать не нужно:

```sql
select * from public.issue_promo('AI_PLUS', 30, 100, '2026-12-31', 'блогер Иванов');
```

Аргументы по порядку: тариф, дней доступа, сколько человек смогут активировать,
до какого числа принимается код (можно `null`), пометка для себя. Код вернётся
в результате запроса — алфавит без `0/O` и `1/I`, чтобы не путались при диктовке.

Нужен конкретный код вместо сгенерированного — шестым аргументом:

```sql
select * from public.issue_promo('AI', 14, 50, null, 'рассылка', 'EATAPS14');
```

Либо обычной вставкой, если так привычнее:

```sql
insert into public.promo_codes (code, tier, days, max_uses, expires_at, note)
values ('EATAPS30', 'AI_PLUS', 30, 100, '2026-12-31', 'блогер Иванов');
```

| Поле | Что задаёт |
|---|---|
| `code` | Сам код. Хранить **в верхнем регистре** — при гашении ввод приводится к нему |
| `tier` | `AI` или `AI_PLUS` |
| `days` | На сколько дней открывается доступ с момента активации |
| `max_uses` | Сколько человек всего смогут его активировать |
| `expires_at` | Когда код перестаёт приниматься; `null` — бессрочно |
| `note` | Для чего выпущен — видно только вам |

Человек вводит код на экране тарифов (вкладка **AI** → «Есть промокод?»).
Один код — одно гашение на аккаунт, это ограничение базы, а не проверка в коде.

Отозвать выдачу (доступ пропадёт при следующей загрузке приложения):

```sql
delete from public.promo_grants where code = 'EATAPS30' and user_id = '<uuid>';
```

Промокод и подписка Stripe независимы: действует тот тариф, который выше.
Оплаченный AI+ не понижается промокодом на AI, а промокод продолжает работать,
даже если подписку отменили.

### Лимиты

Считаются деньгами, а не количеством сообщений: разбор месяца стоит как двадцать
коротких вопросов. Цены и бюджеты — одна таблица в
[`src/lib/aiBudget.js`](src/lib/aiBudget.js); модель по тарифу — там же.

**Решение о лимите принимает база, а не сервер.** Это важно и стоило дыры.
Прежний порядок был такой:

```js
spent = await spentThisPeriod(user)   // 1. прочитали расход
check = checkBudget({ spent, ... })   // 2. решили по прочитанному
await reserve(user, check.needed)     // 3. списали
```

Шаги 1 и 3 разнесены во времени, и между ними ничто не мешало другому запросу
прочитать то же самое число. Сто запросов, отправленных **одновременно**,
читали `spent = 0`, все сто проходили проверку и все сто уходили в модель —
при дневном лимите бесплатного тарифа в три запроса. Платил владелец ключа.

Теперь списание и решение — одна операция (`ai_reserve`, миграция
[`2026-09-12_ai_ledger.sql`](supabase/migrations/2026-09-12_ai_ledger.sql)):
функция списывает, смотрит на **получившийся** итог и при перерасходе
возвращает резерв и отказывает. Гонка невозможна не потому, что «мы успеваем»,
а потому, что проверять нечего — число получено из самой записи.

**Обрывы.** У каждого запроса своя строка в журнале `ai_requests`. Повторная
заявка с тем же идентификатором не списывает дважды, повторный расчёт не
возвращает дважды. Если функция не дожила до расчёта (платформа убила по
таймауту, отвалилась база), резерв вернёт ежедневная `/api/maintenance` —
см. раздел «Регулярная уборка».
