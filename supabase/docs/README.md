# База EatAps — как она устроена и как её менять

Эта папка отвечает на два вопроса: **что сейчас в базе** и **как написать
следующую миграцию так, чтобы она не подралась с предыдущими**.

Читать перед тем, как писать любой SQL для этого проекта.

| Файл | О чём |
|---|---|
| [`catalog.md`](catalog.md) | **Что в базе на самом деле.** Генерируется из исходников — врать не может |
| [`01-model.md`](01-model.md) | Модель данных: кто чем владеет, какие инварианты держат систему |
| [`02-access.md`](02-access.md) | Модель доступа: круги видимости, где живёт каждое правило |
| [`03-pitfalls.md`](03-pitfalls.md) | **Грабли, на которые тут уже наступали.** Самый полезный файл |
| [`04-history.md`](04-history.md) | Карта миграций: что сделала каждая и что отменила |
| [`05-checklist.md`](05-checklist.md) | Чек-лист новой миграции — по нему проверяют перед прогоном |

## Где что лежит

```
supabase/
  migrations/          ← ЕДИНСТВЕННЫЙ источник правды. Только сюда пишут новое
    2026-08-05_initial.sql   первая миграция (бывший schema.sql)
    2026-08-06_…             дальше по датам, порядок = порядок прогона
  setup_all.sql        ← СБОРКА. Генерируется, руками не править
  verify*.sql          ← самопроверки после прогона, только читают
  diagnose_writes.sql  ← точечная диагностика отказов записи
  docs/                ← эта папка
  archive/             ← мёртвые файлы. ЗАПУСКАТЬ НЕЛЬЗЯ, см. archive/README.md
```

**Правило одного источника.** Объект базы описан ровно в одном месте — в той
миграции, где он последний раз менялся. Ни `setup_all.sql`, ни документация,
ни `archive/` источником не являются.

## Как ставится и обновляется база

| Задача | Что делать |
|---|---|
| Поднять базу с нуля | Вставить `supabase/setup_all.sql` в SQL Editor целиком → Run. Одного прогона достаточно |
| Обновить работающую базу | Прогнать только новые миграции по порядку. Либо снова весь `setup_all.sql` — он идемпотентен целиком |
| Проверить, что всё встало | `verify.sql`, `verify_social.sql`, `verify_nickname.sql`, `verify_hardening.sql` — все строки должны быть ✔ |
| Понять, почему не проходит запись | `diagnose_writes.sql` |

`setup_all.sql` **безопасно прогонять повторно на базе с данными**: таблицы
через `create table if not exists`, политики и функции через `drop`/`create`,
бэкфиллы под условием «делаем только при первом появлении колонки».

```bash
node scripts/build-setup-all.mjs          # пересобрать setup_all.sql
node scripts/build-setup-all.mjs --check  # упасть, если он разошёлся с источниками

node scripts/sql-catalog.mjs --check      # упасть, если каталог устарел
node scripts/sql-idempotency.mjs           # переживут ли миграции повторный прогон

node scripts/policy-audit.mjs [таблица]   # итоговый набор RLS-политик
```

Короткие псевдонимы: `npm run sql:build`, `sql:catalog`, `sql:check`,
`sql:idem`, `sql:policies`, и `npm run sql:verify` — все проверки разом.

## Как писать новую миграцию

1. **Прочитать [`03-pitfalls.md`](03-pitfalls.md).** Половина ошибок в этом
   проекте — повторение одной из уже описанных там.
2. **Посмотреть [`catalog.md`](catalog.md)** — как объект выглядит СЕЙЧАС.
   Не открывать старую миграцию и не считать её актуальной: почти каждая
   ключевая функция здесь переписывалась по три-пять раз.
3. Создать `supabase/migrations/YYYY-MM-DD_короткое_имя.sql`.
4. Написать шапку по образцу: что ломается сегодня, почему чиним именно так,
   что произойдёт с существующими данными. Комментарии в этом проекте — часть
   миграции, а не украшение: по ним восстанавливают ход мысли через полгода.
5. Дописать файл в `SOURCES` в `scripts/build-setup-all.mjs` — **в конец**.
6. `npm run sql:build && npm run sql:catalog && npm run sql:verify`.
7. Пройтись по [`05-checklist.md`](05-checklist.md).
8. Прогнать на базе, затем `verify*.sql`.

### Три требования к каждой миграции

**Идемпотентность.** Повторный прогон не должен ничего менять. Не
`create table`, а `create table if not exists`; не `alter table add column`, а
`add column if not exists`; политики и функции — через `drop`/`create` или
`create or replace`. Разовый бэкфилл заворачивают в условие «делаем, только
если колонки ещё не было» — иначе второй прогон затрёт живые данные.

**Порядок не обсуждается.** Каждая миграция рассчитывает на состояние базы
после всех предыдущих. Новый файл идёт строго в конец `SOURCES`. Вставить его
в середину — значит молча сломать установку с нуля.

**Совместимость с работающим фронтендом.** Деплой не атомарен. Миграция,
сужающая доступ, идёт ПОСЛЕ выкладки фронтенда; миграция, добавляющая
возможность, — до. Фронтенд в этом проекте умеет работать с обеими версиями
базы (см. `isMissingRelation` / `isMissingColumn` в `src/lib/supabase.js`),
и это свойство надо сохранять.
