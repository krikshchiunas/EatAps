# Грабли этого проекта

Каждый пункт — ошибка, которая **уже случилась здесь** и стоила живого бага.
Ссылка в конце пункта ведёт на миграцию, где она разобрана подробно.

## 1. `search_path = public` отрезает расширения

Все функции проекта объявлены с `set search_path = public`. В Supabase
расширения живут в схеме `extensions`, и вызов `gen_random_bytes()` из
pgcrypto или тип `citext` внутри такой функции **падает в рантайме**.

Один раз это чуть не приземлилось прямо в триггер регистрации: люди перестали
бы регистрироваться.

**Как обходят здесь:** `gen_random_uuid()` (функция ядра, есть всегда) вместо
`gen_random_bytes`; `text` + check-constraint «только нижний регистр» вместо
`citext`.

*(2026-08-09_unpredictable_public_id, 2026-08-25_social_graph)*

## 2. `create or replace` не умеет менять набор колонок

У функции, возвращающей `table (...)` или `setof`, набор OUT-параметров —
часть её типа. Попытка сменить хотя бы одно имя колонки:

```
42P13: cannot change return type of existing function
DETAIL: Row type defined by OUT parameters is different.
```

**Правильно:**

```sql
drop function if exists public.list_posts(uuid, int, timestamptz);
create or replace function public.list_posts(...) ...;
-- ↓ ОБЯЗАТЕЛЬНО: drop забирает права с собой
revoke all on function public.list_posts(uuid, int, timestamptz) from public, anon;
grant execute on function public.list_posts(uuid, int, timestamptz) to authenticated;
```

Забытый `grant` после `drop` = `permission denied for function` у всех
пользователей, при том что функция в базе есть и в SQL Editor работает.

### Раннее создание — тоже мина

Самая коварная разновидность: функцию создали **один раз** через
`create or replace`, drop не нужен — всё честно. Потом более поздняя миграция
добавила колонку в возвращаемый набор и свой drop поставила. Раннее создание
осталось без него.

На чистой базе всё проходит: функции ещё нет, `create or replace` просто
создаёт. А вот **повторный прогон `setup_all.sql` поверх уже мигрированной
базы** упирается ровно в эту строку — старая редакция пытается лечь поверх
новой формы и получает 42P13. То есть ошибка видна только в том сценарии,
который и есть основной способ обновления.

Так сломались `list_posts` (получила `visibility` в `2026-08-25`, создание из
`2026-08-11` осталось голым) и `user_brief`.

**Правило:** если хоть одна миграция меняет набор колонок функции — drop
обязан стоять перед **каждым** её созданием, включая самое первое.
Проверяется тестом «функции со сменившимся набором колонок создаются
защищённо» в `src/lib/sqlGuard.test.js`.

### Когда drop не спасает: тело ссылается на удалённую колонку

`user_brief` из `2026-08-23` отдавала `(public_id, name)` и читала
`p.public_id`. Колонки нет с `2026-08-26`, а тело на `language sql`
проверяется **при создании** — значит, к 42P13 добавляется ещё и 42703.

Drop тут бесполезен: проблема не в замене, а в том, что старую редакцию
вообще нельзя создать. Единственный выход — не создавать её на базе, где
условия для неё уже нет:

```sql
do $$
begin
  if exists (
    select 1 from information_schema.columns
    where table_schema='public' and table_name='profiles' and column_name='public_id'
  ) then
    execute $fn$ create or replace function public.user_brief(...) ... $fn$;
    execute 'grant execute on function public.user_brief(uuid) to authenticated';
  end if;
end $$;
```

На свежей базе шаг истории выполняется, на мигрированной — пропускается.
Тот же приём применён к `touch_last_seen` в первой миграции.

**Не полагаться на то, какая форма функции лежит в конкретной базе.** Историю
этого проекта накатывали по-разному — отдельными файлами, склейкой, правками
из редактора. Поэтому снимают и создают заново, а не надеются на совпадение.
Если возможных старых сигнатур несколько — снимают все:

```sql
drop function if exists public.list_post_comments(uuid, int);
drop function if exists public.list_post_comments(uuid, int, timestamptz, uuid);
```

*(2026-08-25_social_graph §20, 2026-09-05_social_hardening §5.2, §7)*

## 3. Новый аргумент с `default` создаёт перегрузку, а не заменяет функцию

`ai_usage_add(uuid, text, bigint)` + новая версия `(uuid, text, bigint, boolean
default true)` = **две функции**. Вызов с тремя аргументами становится
неоднозначным, Postgres отказывается выбирать.

**Правильно:** явно снести старую сигнатуру перед созданием новой.

*(2026-08-24_ai_usage)*

## 4. Подзапрос внутри RLS-политики подчиняется RLS другой таблицы

Самая дорогая ошибка проекта. Политика подписок выглядела так:

```sql
and not exists (
  select 1 from public.blocks b
  where (b.blocker_id = following_id and b.blocked_id = follower_id)
     or (b.blocker_id = follower_id  and b.blocked_id = following_id)
)
```

Замысел: нельзя подписаться ни на того, кого заблокировал я, ни на того, кто
заблокировал меня. **Работала только вторая половина.** Выражение политики
выполняется от имени вызывающего, а у `blocks` своя политика
`using (auth.uid() = blocker_id)` — строку «он заблокировал меня» я не вижу,
подзапрос её не находит, ветка всегда ложна.

**Правильно:** любую проверку, которой нужно видеть обе стороны, выносят в
`SECURITY DEFINER`-функцию. В проекте это `is_blocked_between`,
`is_friend_with`, `can_view_post`, `in_challenge`.

**Общее правило:** внутри политики можно вызывать только `SECURITY DEFINER`-
функции; прямой подзапрос к таблице с RLS почти всегда врёт.

*(2026-09-05_social_hardening §5.1.2)*

## 5. Политика, читающая свою же таблицу, зацикливается

Политика на `posts`, вызывающая `can_view_post()`, которая читает `posts`, —
бесконечная рекурсия. То же с `challenge_members` и `in_challenge`.

**Правильно:** либо `SECURITY DEFINER` в функции (разрывает цепочку RLS), либо
предикат прямо в политике. В `posts` живут **оба** — политика повторяет логику
`can_view_post` выражением, и это дублирование намеренное. Меняя одно, надо
менять и второе.

*(2026-08-11_profile_and_thoughts §3, 2026-08-25_social_graph §11)*

## 6. Порядок триггеров — алфавитный

Внутри одной таблицы Postgres выполняет сначала все BEFORE, потом INSTEAD OF,
потом AFTER — и **внутри каждой группы в алфавитном порядке имён**.

Здесь это несущее свойство: `follows_aa_pair_lock` назван так, чтобы идти
раньше `follows_rate_limit`, потому что advisory-лок должен быть взят до любой
другой проверки. Переименование сломает сериализацию пары подписок молча.

Итоговый порядок по каждой таблице — в [`catalog.md`](catalog.md#триггеры).

*(2026-09-05_social_hardening §2)*

## 7. `auth.uid()` внутри `SECURITY DEFINER` — это по-прежнему вызывающий

`SECURITY DEFINER` меняет роль, но **не JWT**. Внутри такой функции
`auth.uid()` возвращает того же человека, что и снаружи.

На этом сгорел `guard_profile_update`: он откатывал правки `display_name` и
`avatar_url` по условию «есть `auth.uid()`», считая, что у серверной записи его
не будет. Условие оказалось истинным и для законной зеркалящей функции —
публичная витрина перестала обновляться вообще, и у всех новых аккаунтов имя и
аватар остались пустыми.

**Правильно:** различать законную запись явным признаком, а не косвенным:

```sql
perform set_config('eataps.trusted_profile_write', 'on', true);  -- true = на транзакцию
update public.profiles set ... where user_id = ...;
perform set_config('eataps.trusted_profile_write', 'off', true);
```

и в guard-триггере:

```sql
if auth.uid() is not null
   and coalesce(current_setting('eataps.trusted_profile_write', true), 'off') <> 'on' then
  new.username := old.username;  -- откатываем всё, что пришло не от сервера
  ...
end if;
```

Третий аргумент `set_config` = `true` обязателен: признак живёт до конца
транзакции и не может утечь на соседний запрос через пул соединений.

*(2026-09-05_social_hardening §11.1)*

## 8. Тело PL/pgSQL проверяется в рантайме, а не при создании

`create function` с обращением к несуществующей колонке в теле PL/pgSQL
проходит **без единой жалобы**. Падает потом — на каждой строке, где триггер
срабатывает.

Так и вышло: колонку `profiles.public_id` удалили, а `guard_profile_update` её
всё ещё читал. Файл прогнался чисто, а дальше `42703 record "new" has no field
public_id` ронял **каждый UPDATE по profiles** — то есть смену ника и всё
сохранение состояния.

Заметили не сразу: зеркалящий триггер обновляет строку только при расхождении,
у старых аккаунтов расхождения нет. Ошибку встречал ровно тот, кто завёл
аккаунт после миграции. То есть каждый новый человек.

**Правило:** удаляя колонку, надо пройти **grep'ом по всем телам plpgsql** —
и в триггерах, и в guard-функциях. Функции на `language sql` в этом смысле
безопаснее: их тело проверяется при создании.

*(2026-09-05_social_hardening §11.1, `diagnose_writes.sql` проверка №9)*

## 9. `alter publication ... add table` падает на повторе

```sql
alter publication supabase_realtime add table public.messages;
```

при втором прогоне — ошибка, и весь файл встаёт. Поэтому в проекте всегда:

```sql
do $$
begin
  if not exists (
    select 1 from pg_publication_tables
    where pubname = 'supabase_realtime' and schemaname = 'public' and tablename = 'messages'
  ) then
    execute 'alter publication supabase_realtime add table public.messages';
  end if;
end $$;
```

И отдельно: **realtime-фильтры по UPDATE не работают без `replica identity
full`** — в WAL уезжает только первичный ключ, и `sender=eq.…` не матчится.
Без этого статус прочтения не долетал бы до отправителя.

*(2026-08-05_initial, 2026-08-25_social_graph §23)*

## 10. Supabase раздаёт права на новые объекты автоматически

Новым таблицам и **представлениям** по умолчанию достаются привилегии для
`anon` и `authenticated`. Представление `admin_subscriptions` читает
`auth.users`, то есть почты живых людей: без явного отзыва любой вошедший
выгрузил бы всю базу пользователей одним запросом.

**Правило:** всё «для владельца» получает явный `revoke ... from anon,
authenticated` и `grant ... to service_role` сразу после создания.

*(2026-08-25_admin_views)*

## 11. Отсутствие политики надёжнее политики, которая ничего не разрешает

Если на таблице включён RLS и **нет** политики на команду — команда запрещена
всем, кроме `service_role`. Здесь это используют как основную защиту:

- у `notifications` нет INSERT-политики → клиент физически не может создать
  уведомление никому, включая себя;
- у `post_comments` нет UPDATE-политики → комментарий нельзя отредактировать;
- у `bans`, `support_messages`, `promo_codes` нет ничего, кроме чтения своего;
- у `profiles` UPDATE-политику **удалили**, потому что guard-триггер и так
  откатывал все колонки: «политика, которая ничего не разрешает, — это
  обещание, что когда-нибудь кто-нибудь добавит колонку и забудет про guard».

*(2026-08-25_social_graph §8, 2026-09-05_social_hardening §11.1)*

## 12. Ужесточать функцию, оставляя таблицу открытой, бессмысленно

`list_followers` научили прятать заблокированных — а политика `follows`
оставалась `using (auth.role() = 'authenticated')`. Любой вошедший читал
таблицу целиком мимо RPC:

```
GET /rest/v1/follows?follower_id=eq.<uuid>
```

То же было с `post_comments`: функция фильтровала заблокированных, политика —
нет.

**Правило:** правило доступа ставят **и в RPC, и в политику таблицы**, либо
таблицу закрывают от прямого чтения вовсе. Проверить, что клиент реально
читает напрямую, легко:

```bash
grep -rn "\.from('таблица')" src api
```

*(2026-09-05_social_hardening §5.3.1, §7)*

## 13. Бэкфилл должен срабатывать ровно один раз

`update ... set read_at = created_at` в файле, который прогоняют повторно,
на втором прогоне затрёт настоящие непрочитанные.

**Правильно:** привязать бэкфилл к необратимому событию — появлению колонки:

```sql
do $$
begin
  if not exists (
    select 1 from information_schema.columns
    where table_schema='public' and table_name='messages' and column_name='read_at'
  ) then
    alter table public.messages add column read_at timestamptz;
    update public.messages set read_at = created_at;   -- только здесь
  end if;
end $$;
```

Тот же приём: `posts.visibility_migrated`, бэкфилл ников `where username is null`,
перевыдача ID `where public_id !~ '<новый формат>'`.

*(2026-08-05_initial, 2026-08-25_social_graph §10, 2026-08-26_nickname_identity §4)*

## 14. Бэкфилл циклом, если значения зависят друг от друга

`claim_username` проверяет занятость обычным `select` — а он **не видит строки,
вставляемые тем же запросом**. Один `update` на всех выдал бы двум людям с
одинаковым именем один ник и упал бы на уникальном индексе.

Поэтому ники раздаёт `do $$ … for r in … loop … end loop $$` — по одному, и
каждый следующий видит предыдущего.

*(2026-08-26_nickname_identity §4)*

## 15. Порядок ВНУТРИ файла тоже значим

Postgres проверяет выражение политики в момент её создания. Политика `follows`
ссылается на `public.blocks` — значит, `blocks` создаётся в том же файле
**выше**, не в своём тематическом разделе ниже. Иначе `relation does not exist`.

То же с `drop column`: сначала снимают функции, которые колонку читают, потом
саму колонку — иначе `DROP COLUMN` упрётся в зависимости.

*(2026-08-25_social_graph §5, 2026-08-26_nickname_identity §3)*

## 16. `on conflict` по частичному индексу требует того же предиката

```sql
create unique index notifications_dedup_idx
  on public.notifications (recipient_id, actor_id, type, entity_id)
  where entity_id is not null;
```

```sql
insert into public.notifications (...) values (...)
on conflict (recipient_id, actor_id, type, entity_id)
  where entity_id is not null          -- ← без этой строки: 42P10
do update set ...;
```

Без совпадающего предиката Postgres отвечает `42P10 there is no unique or
exclusion constraint matching the ON CONFLICT specification` — и падает
**каждая подписка и каждое сообщение**, потому что обе идут через
`push_notification`. Это первое, что проверяет `diagnose_writes.sql`.

*(2026-08-25_social_graph §8)*

## 17. Гонка двух транзакций на READ COMMITTED

Дружба возникает, когда подписка стала взаимной: триггер на `follows` смотрит,
есть ли встречная строка. Пока подписываются по очереди — сходится. Если обе
вставки идут одновременно, ни одна транзакция не видит незакоммиченную строку
другой, условие ложно у обеих: **взаимная подписка есть, дружбы нет**.

Пара оказывалась в состоянии «переписываться можно, дневник не виден, в списке
друзей друг друга нет», и починить это человек не мог.

**Лечится с двух сторон, и обе нужны:**

1. Сериализация пары транзакционным advisory-локом в **BEFORE**-триггере (в
   AFTER поздно: снимок второй транзакции всё равно приедет старый):
   ```sql
   perform pg_advisory_xact_lock(
     hashtextextended(least(a,b)::text || '|' || greatest(a,b)::text, 20260905));
   ```
2. Снятие зависимости прав от материализованной строки: и политика дневника, и
   списки, и счётчики считаются через `is_friend_with` (подписки), а строка
   `friendships` осталась только якорем уведомления.

**Общий вывод:** если у понятия два определения — вычисляемое и
материализованное, — рано или поздно они разойдутся. Права считают по
вычисляемому.

*(2026-09-05_social_hardening §1–§5)*

## 18. Пара `(A,B)` и `(B,A)` — для базы разные строки

`unique (requester, addressee)` не мешает существовать обеим. Пока строку
создавал человек заявкой, вторая была невозможна по смыслу; как только её стал
создавать триггер по обеим подпискам — гонка дала две строки дружбы и два
уведомления об одном событии.

**Правильно:** уникальность по неупорядоченной паре, и дедупликация **до**
создания индекса:

```sql
delete from public.friendships f using public.friendships g
where least(f.requester,f.addressee) = least(g.requester,g.addressee)
  and greatest(f.requester,f.addressee) = greatest(g.requester,g.addressee)
  and (f.created_at, f.id) > (g.created_at, g.id);

create unique index if not exists friendships_pair_uniq
  on public.friendships (least(requester, addressee), greatest(requester, addressee));
```

*(2026-09-05_social_hardening §1)*

## 19. Форма условия решает, ляжет ли запрос на индекс

Две вещи, найденные здесь на живых запросах:

- **Пара собеседников.** `messages_pair_idx` построен по
  `(least(sender,recipient), greatest(sender,recipient), created_at desc)`.
  Клиентская форма `(sender=a and recipient=b) or (sender=b and recipient=a)`
  этим индексом воспользоваться **не может** — нужна форма через
  `least/greatest`.
- **Список диалогов.** `where sender = me or recipient = me` не ложится ни на
  один индекс и читает таблицу сообщений **всех** пользователей. Правильная
  форма — `union all` из двух половин: каждая ложится на свой индекс.

*(2026-09-05_social_hardening §13.4, §13.5)*

## 20. Offset-пагинация врёт на дописываемом сверху списке

Пока человек листает ленту, сверху приезжают новые посты и сдвигают окно —
он видит дубли. Везде, где список пополняется с головы, используется keyset по
`(created_at, id)`:

```sql
where (p_before_at is null
   or (p.created_at, p.id) < (p_before_at, coalesce(p_before_id, '00000000-…-0'::uuid)))
order by p.created_at desc, p.id desc
```

`offset` оставлен только в `list_followers` / `list_following` / `list_friends`,
где порядок стабилен.

Отдельная ошибка того же класса: `order by created_at asc limit 300` в чате
брал **самые старые** триста сообщений — в длинной переписке человек не видел
ни одного свежего. Читать историю надо с конца, а переворачивать на клиенте.

*(2026-08-25_social_graph §19, 2026-09-05_social_hardening §7, §13.4)*

## 21. Связанный `select` выдаёт больше, чем счётчик

`posts` со связанными `post_reactions` вернёт **строки** реакций, то есть
поимённый список отреагировавших — кусок списка друзей автора, включая людей,
которых спрашивающий не знает.

Поэтому политика `post_reactions` отдаёт **только свою строку**, а наружу
уходят исключительно счётчики — из `list_feed` / `list_posts`. Это и есть
причина, по которой чтение ленты сделано через RPC, а не через PostgREST.

*(2026-08-11_profile_and_thoughts §4, §6)*

## 22. Проверка права должна происходить в момент действия

## 23. Идемпотентность записи на стороне клиента

Отправка сообщения обычным INSERT: ответ потерялся в сети → клиент повторил →
в переписке два одинаковых сообщения. Причём именно на плохой сети, то есть
ровно тогда, когда это заметнее всего.

**Правильно:** ключ, который клиент придумывает **один раз на сообщение** и
повторяет при каждой попытке, плюс частичный уникальный индекс по нему, плюс
обработка `unique_violation` как успеха:

```sql
create unique index if not exists messages_sender_client_idx
  on public.messages (sender, client_id) where client_id is not null;
```

`where client_id is not null` обязателен: у старых сообщений ключа нет, и
миллионы NULL в уникальном индексе не нужны никому.

*(2026-09-05_social_hardening §13.1, §13.3)*

## 24. Кириллица — в комментариях, латиница — в данных

пишут латиницей: они проходят через буфер обмена, редактор и SQL-консоль, и на
любом стыке могут побиться. Комментарии на русском такой проблемы не создают —
они никуда не отдаются.

## 26. Переименовал политику — сними и новое имя тоже

`drop policy if exists` снимает **старое** имя. Про новое забывают, потому что
на чистой базе его и правда ещё нет:

```sql
drop policy if exists "read own public_id" on public.profiles;
drop policy if exists "profiles select"    on public.profiles;
create policy "profiles select own" on public.profiles ...;   -- 42710 на повторе
```

```
42710: policy "profiles select own" for table "profiles" already exists
```

Ровно как с функциями (§2): ошибка живёт только в сценарии «прогнать
`setup_all.sql` поверх работающей базы», то есть в основном способе обновления.
Сорвала обновление прода после того, как та же мина на `list_posts` была
починена — второй заход, тот же класс.

**Правило без исключений:** перед `create policy "X"` стоит
`drop policy if exists "X"` **с тем же именем и той же таблицей**. Старые имена
снимаются дополнительно, а не вместо. То же для `create trigger`,
`add constraint` и `create view`.

Проверяется автоматически:

```bash
npm run sql:idem
```

Скрипт проходит всю цепочку и требует, чтобы каждое создание объекта было либо
под `if not exists`, либо под своим же `drop … if exists`, либо внутри
условного `do`-блока. Он же в `npm run sql:verify` и в тесте «миграции
переживают повторный прогон».

## 27. Ужесточил CHECK — сначала приведи данные

`add constraint … check (…)` проверяется по **всем существующим строкам**.
Одна не подходит — падает вся транзакция:

```
23514: check constraint "ai_usage_period_check" of relation "ai_usage"
       is violated by some row
```

Так и вышло у `ai_usage`: приложение перешло на дневной учёт, миграция сменила
формат периода с `YYYY-MM` на `YYYY-MM-DD` — а строки старого, месячного
формата остались лежать. На пустой базе проходит, на живой роняет прогон
посреди файла.

**Правило:** подмена CHECK на таблице с данными — это всегда ДВА шага, и
порядок обязателен:

```sql
alter table T drop constraint if exists C;   -- 1. снять старое
-- 2. привести данные (перенести, пересчитать, почистить)
alter table T add constraint C check (…);    -- 3. поставить новое
```

Перенос идёт **между** ними: пока старое ограничение живо, значения нового
формата в таблицу не вставить.

Данные при этом не выбрасывают, если они что-то значат. `ai_usage` — учёт
денег, поэтому месяц переносится на своё первое число: суммы сохраняются
целиком, теряется только гранулярность, которой у этих строк и не было.
Строки неизвестного формата не удаляются молча — миграция останавливается с
внятным сообщением, потому что решать их судьбу должен человек.

### Что важно про имена

У `check` без имени Postgres генерирует своё: `<таблица>_<колонка>_check`.
Именно поэтому анонимный `period text not null check (…)` из одной миграции и
явный `add constraint ai_usage_period_check` из другой — **одно и то же
ограничение**, хотя по тексту это не видно. Первая редакция автоматической
проверки на этом и споткнулась: не знала про генерируемые имена и считала, что
подмены нет.

Проверяется `npm run sql:idem` — он сверяет предикаты по всей цепочке (включая
безымянные) и требует шага с данными, если условие ужесточается. Расширение
списка значений (`in ('A','B')` → `in ('A','B','C')`) пропускается: сломать
существующие строки оно не может.

## 28. Удалённая колонка живёт в ранних миграциях

Прямое продолжение §8, но с другой стороны. Там речь была про функцию,
пережившую удаление колонки. Здесь — про то, что **ранние миграции
по-прежнему её создают и читают**, и на уже мигрированной базе повторный
прогон до них доходит.

`profiles.public_id` удаляет `2026-08-26`. Всё, что стоит раньше и трогает эту
колонку, при повторном прогоне падает:

```
42703: column "public_id" does not exist
QUERY:  select user_id from public.profiles
        where public_id = public.normalize_public_id(p_public_id)
```

**Ловушка в том, что это состояние достижимо не сразу.** Пока колонка ещё жива
на проде, прогон проходит целиком — и сам же её удаляет. Ошибка появляется
только на СЛЕДУЮЩЕМ прогоне. Здесь так и вышло: один прогон завершился без
единой жалобы, второй встал.

### Три разных места, три разных срока срабатывания

| Что ссылается | Когда падает |
|---|---|
| Тело `language sql` | **при создании функции** — тело проверяется сразу |
| Обычный DML/DDL (`insert`, `update`, `add constraint`) | при выполнении, то есть тут же |
| Тело `language plpgsql` | **не падает при создании вовсе** — но взрывается при каждом вызове |

Третья строка — самая коварная. `guard_profile_update` из `2026-08-25` читал
`new.public_id`; миграция прогонялась чисто, а дальше падал каждый `update` по
`profiles`, то есть смена ника и всё сохранение состояния (§8).

### Как чинят

Историческую часть ставят под условие. На свежей базе она нужна как шаг
истории, на мигрированной — пропускается целиком:

```sql
do $$
begin
  if exists (
    select 1 from information_schema.columns
    where table_schema='public' and table_name='profiles' and column_name='public_id'
  ) then
    execute $fn$ create or replace function … $fn$;
    execute 'grant execute on function … to authenticated';
    insert into public.profiles (user_id, public_id) …;   -- обычный DML можно прямо здесь
  end if;
end $$;
```

Внутри `do`-блока обычные операторы готовятся лениво: если условие ложно, до
них дело не доходит и ошибки нет. А вот `create function` требует `execute`.

Проверяется `npm run sql:idem`: он находит все колонки, которые удаляет любая
миграция, и требует, чтобы более ранние ссылки на них были под условием.
Ссылки внутри тел plpgsql он пропускает как безопасные при создании — но
отдельно ловит `new.<колонка>` / `old.<колонка>`, то есть ровно тот случай,
когда функция триггерная и падать будет на живых записях.

## 29. `alter type … add value` не переживает прогон одним куском

`setup_all.sql` вставляют в SQL Editor **целиком**, и он выполняется одной
транзакцией. Расширить перечисление внутри неё можно, а ВОСПОЛЬЗОВАТЬСЯ новым
значением — нет:

```
55P02: unsafe use of new value "close_friends" of enum type post_visibility
```

Пока значение только добавляют, всё тихо. Ловушка срабатывает, когда более
поздняя строка того же файла ставит новое значение в `DEFAULT`, в `CHECK` или
просто вставляет строку с ним — то есть при первой же попытке использовать то,
ради чего перечисление и расширяли.

**Как чинят.** Перечисления, которые будут расширяться, держат как `text` с
`CHECK`. Расширение списка тогда — обычная правка ограничения, и она
выполняется в той же транзакции без оговорок.

В `2026-09-09_social_graph_v2` так переведены три типа: `post_visibility`,
`diary_audience` и `notification_type`. Перевод колонки делается под условием
«тип ещё не text», иначе повторный прогон спотыкается о собственную работу:

```sql
do $$
begin
  if exists (
    select 1 from information_schema.columns
    where table_schema='public' and table_name='posts'
      and column_name='visibility' and data_type <> 'text'
  ) then
    alter table public.posts alter column visibility drop default;
    alter table public.posts alter column visibility type text using visibility::text;
    alter table public.posts alter column visibility set default 'followers';
  end if;
end $$;
```

`drop default` перед сменой типа обязателен: значение по умолчанию имеет тип
старого перечисления, и `alter column … type` о него спотыкается.

## 30. Политика, читающая свою же таблицу, зацикливается

RLS-политика на `conversation_members`, которой нужно знать «а состоит ли этот
человек в диалоге», не может спросить об этом `conversation_members` обычным
подзапросом: проверка политики запустит ту же политику, и та снова её же.

```
42P17: infinite recursion detected in policy for relation "conversation_members"
```

**Как чинят.** Вопрос выносят в `SECURITY DEFINER`-функцию: она читает таблицу
от имени владельца, для которого RLS не применяется, и рекурсии не возникает.

```sql
create or replace function public.is_conversation_member(p_conversation uuid, p_user uuid)
returns boolean language sql stable security definer set search_path = public
as $$ select exists (select 1 from public.conversation_members m
                      where m.conversation_id = p_conversation
                        and m.user_id = p_user and m.left_at is null); $$;
```

То же самое стоит за `is_blocked_between`, `can_view_diary` и
`can_view_profile_content`: всем им нужно видеть таблицы целиком, а политики
этих таблиц отдают вызывающему только его собственные строки.

⚠ У `SECURITY DEFINER` есть цена: функция обязана быть узкой и не принимать
`user_id` там, где можно взять `auth.uid()`. Функция, которой передают, «от
чьего имени спросить», — это дыра, а не проверка.

## 31. Две SELECT-политики складываются по ИЛИ

Политики одной команды на одной таблице **объединяются**, а не пересекаются.
Вторая политика ничего не ужесточает — она РАСШИРЯЕТ доступ, и более мягкая
молча отменяет более строгую.

Опаснее всего это выглядит при замене правила: написали новую политику с новым
именем, старую снять забыли — и доступ остался прежним, хотя в коде видна
новая, правильная проверка.

**Как чинят.** Перед `create policy` всегда стоит `drop policy if exists` со
всеми историческими именами этой политики, а не только с текущим:

```sql
drop policy if exists "presence select self or friends" on public.presence;
drop policy if exists "presence select by diary visibility" on public.presence;
drop policy if exists "presence select by activity setting" on public.presence;
create policy "presence select by activity setting" on public.presence …;
```

`verify_privacy.sql` проверяет это прямо: у `app_state` и `posts` должно быть
**ровно по одной** SELECT-политике. Не «есть правильная», а «нет второй».

## 32. `security definer` и RLS: функция обходит политику, и это надо помнить

`SECURITY DEFINER`-функция выполняется от имени владельца (`postgres`), а
владелец таблицы RLS не применяет. Значит, ЛЮБАЯ такая функция — это дыра
ровно настолько, насколько небрежно она написана.

Три правила, которые здесь соблюдаются без исключений:

1. **`auth.uid()` вместо параметра.** Действующее лицо берут из сессии, а не из
   аргумента. `accept_follow_request(p_requester)` принимает только ВТОРУЮ
   сторону; адресат — всегда `auth.uid()`, и подставить чужой невозможно по
   построению.
2. **`set search_path = public`.** Без него вызывающий может подсунуть свою
   схему с одноимённой таблицей и заставить функцию работать с ней.
3. **`revoke … from public, anon` + точечный `grant … to authenticated`.**
   Функция, доступная `anon`, — это функция, доступная интернету.

`verify_social_v2.sql` и `verify_privacy.sql` проверяют третий пункт списком
имён: новая функция, забытая в `revoke`, всплывает там же.
