# Модель данных

Полный перечень таблиц, колонок и индексов — в [`catalog.md`](catalog.md).
Здесь то, чего в каталоге нет: **кто чем владеет, какими путями туда пишут и
какие инварианты держат систему**.

---

## Общий принцип: local-first + один блоб

Приложение хранит всё состояние человека одним JSON-объектом в
`app_state.state`. Дневник, профиль, настройки, свои продукты — всё там.

Отдельными таблицами вынесено ровно то, что **не помещается в эту модель по
одной из трёх причин**:

| Причина | Примеры |
|---|---|
| Растёт без предела | `messages`, `posts`, `notifications`, `ai_usage` |
| Читается другими людьми и требует собственных прав | `posts`, `post_comments`, `profiles` |
| Пишется сервером, а не человеком | `subscriptions`, `bans`, `promo_grants`, `ai_usage` |

Заводя новую сущность, надо честно ответить, попадает ли она хоть в одну
строку этой таблицы. Если нет — её место в блобе.

## Кто чем владеет

«Владеет» = единственный путь записи. Всё остальное закрыто на уровне прав.

| Таблица | Кто пишет | Как именно |
|---|---|---|
| `app_state` | человек, но только через RPC | `save_app_state()`. Прямые INSERT/UPDATE **отозваны** у `anon`/`authenticated` |
| `presence` | сервер | `touch_last_seen()`. Прямая запись отозвана |
| `profiles` | сервер | `handle_new_user()` при регистрации, `set_username()`, `sync_profile_from_state()`. Клиентской UPDATE-политики нет |
| `follows` | человек | прямой INSERT только на ОТКРЫТЫЙ аккаунт; на закрытый — только `accept_follow_request()` |
| `follow_requests` | **только RPC** | `follow_user()` создаёт, DELETE-политика позволяет отозвать и отклонить |
| `blocks` | человек | прямые INSERT/DELETE либо `block_user()`; последствия — триггер `apply_block` |
| `close_friends`, `restricted_users`, `user_mutes`, `diary_access` | человек | прямые запросы, всё проверяет RLS: писать можно только в свою строку |
| `friendships` | **только триггер** | производная от `follows`, см. ниже. Клиентские политики записи сняты |
| `conversations` | **только RPC** | `direct_conversation()`, `create_group_conversation()` |
| `conversation_members` | **только RPC** | INSERT-политики нет вовсе; своя строка обновляется под guard-триггером |
| `messages` | человек | `send_conversation_message()` (RPC), плюс `mark_conversation_read()`, `set_message_reaction()`, `unsend_message()` |
| `message_deletions`, `message_views` | человек | прямой INSERT только про себя |
| `notifications` | **только триггеры** | `push_notification()`. INSERT-политики нет вовсе |
| `posts`, `post_comments` | человек | прямые INSERT/DELETE |
| `post_reactions` | человек | `toggle_post_reaction()`; политики — второй слой |
| `subscriptions` | сервер | вебхук Stripe через `service_role` |
| `promo_codes` | владелец приложения | `issue_promo()` из SQL Editor |
| `promo_grants` | сервер | `redeem_promo()` |
| `ai_usage` | сервер | `ai_usage_add()`, доступна только `service_role` |
| `bans`, `support_messages`, `coaches` | сервер | функции в `api/`, через `service_role` |
| `coach_links`, `day_comments`, `challenge*` | человек | прямые запросы, всё проверяет RLS |

## Инварианты

Свойства, которые обязаны выполняться всегда. Их проверяют `verify*.sql`.

### 1. СВЯЗЬ — НЕ ПРАВО

Главный инвариант системы с 2026-09-09. Ни один признак связи не является
разрешением сам по себе.

```
follows(A→B)              — A читает B. Даёт доступ ТОЛЬКО к тому,
                            что B пометил как «для подписчиков».
follows(A→B) и follows(B→A) — взаимная подписка. Сверх двух подписок
                            не даёт НИЧЕГО.
follow_requests(A→B)      — просьба. Прав не даёт вовсе.
```

Право доступа к каждому ресурсу считает **ровно одна функция**, и она же стоит
в политике этого ресурса:

| Ресурс | Функция | Политика |
|---|---|---|
| содержимое профиля | `can_view_profile_content()` | предикат `posts select` |
| запись | `can_view_post()` | `posts select` (предикат развёрнут) |
| дневник | `can_view_diary()` | `app_state select` |
| присутствие | `can_see_activity()` | `presence select` |
| право писать | `get_message_permission()` | `messages insert` (через `can_message`) |
| членство в диалоге | `is_conversation_member()` | `conversations`, `messages`, storage |

Эта ошибка случалась дважды и оба раза дорого: сначала «дружба» была
одновременно фактом и правом, потом её роль пыталась занять взаимная подписка.
В обоих случаях расхождение в графе становилось расхождением в правах — пара
оказывалась в состоянии «переписываться можно, дневник не виден, в списке
друзей друг друга нет» (см. [pitfalls §17](03-pitfalls.md)).

`friendships` остаётся ПРОИЗВОДНОЙ от `follows` (её ведёт триггер) и служит
единственной цели — якорю уведомления «теперь вы друзья». Ни одна проверка
прав её не читает.

Полная модель — в [`docs/social-system.md`](../../docs/social-system.md).

### 1b. Закрытый аккаунт перекрывает настройки

`profiles.is_private = true` означает «мой контент только для одобренных
подписчиков» — и это правило СИЛЬНЕЕ любой настройки видимости. Запись,
помеченная `public`, и дневник с кругом `public` у закрытого аккаунта
посторонним не видны.

Исключений ровно два, и оба выданы владельцем руками конкретному человеку:
`diary_access` (поимённый доступ к дневнику) и `coach_links` (тренер).

### 2. Ник — единственный адрес человека

`profiles.username`: NOT NULL, UNIQUE, `^[a-z0-9_]{3,20}$`, только нижний
регистр. Публичного 12-символьного кода больше нет — колонка и четыре функции
вокруг неё удалены в `2026-08-26_nickname_identity`.

Регистр закреплён в базе не для красоты: уникальный индекс по `text` различал
бы `Andrej` и `andrej`, и два человека получили бы визуально неотличимые
адреса. Менять ник можно не чаще раза в сутки (`username_changed_at`).

### 3. `display_name` и `avatar_url` — копия, а не оригинал

Оригинал лежит в `app_state.state->'profile'`. Публичную копию в `profiles`
поддерживает триггер `app_state_profile_sync`. Прямая запись в эти колонки
откатывается guard-триггером.

Аватар — не ссылка, а data-URL (base64 JPEG 256×256, десятки килобайт).
Потолок 300 000 символов. **Сверх потолка пишут NULL, а не обрезают:**
обрезанный base64 — не «картинка поменьше», а мусор, который браузер не
покажет; пусто честнее, интерфейс нарисует инициал.

### 4. Состояние версионируется, время ставит сервер

`app_state.revision` растёт при каждой записи. `save_app_state(state,
base_revision)` применяет правку, только если с момента чтения никто другой не
писал; иначе возвращает `out_conflict = true` и актуальную версию для слияния.

`updated_at` ставит сервер (`now()`), а не клиент: часы устройств расходятся,
и клиентское время нельзя использовать как порядок записей.

Потолок состояния — 5 МБ.

### 5. Уведомление живёт не дольше того, о чём рассказывает

`entity_id` — не внешний ключ (типы сущностей разные), каскад его не чистит.
Поэтому удаление поста, комментария, дружбы или появление блокировки чистят
уведомления триггерами. Иначе в центре событий остаются записи, ведущие в
никуда.

Дедупликация — частичным уникальным индексом по
`(recipient_id, actor_id, type, entity_id)`. Для `MESSAGE` ключом служит **id
собеседника**, а не сообщения: нужен факт «в этом диалоге есть новое», и вести
он должен к диалогу. Для `POST_COMMENT` — наоборот, id комментария: десять
ответов не должны схлопываться в одну строку.

### 6. Прогресс челленджа не хранится

Он вычисляется на клиенте из дневника, который участники и так открывают друг
другу. В базе только сам челлендж, состав участников и ежедневная отметка
`scored`, которую ставит сам участник. Хранить копию прогресса значило бы
завести второй источник правды, который разойдётся с дневником.

### 7. Два независимых источника платного доступа

`subscriptions` (Stripe) и `promo_grants` (промокоды) **не связаны**.
Действующий тариф — лучший из двух (`bestTier` в `src/lib/subscription.js`,
и та же логика продублирована в представлении `admin_subscriptions`).

Причина: строкой в `subscriptions` владеет вебхук Stripe, он делает upsert
целиком на каждое событие и при отмене принудительно ставит `tier = 'FREE'`.
Доступ, выданный промокодом, там просто стёрся бы — молча и в произвольный
момент.

Ранг тарифов: `FREE`=0, `AI`=1, `AI_PLUS`=2, `AI_PREMIUM`=3.

### 8. Расход ассистента считается в деньгах и по дням

`ai_usage`: строка на пару (пользователь, **день UTC**), формат периода
`YYYY-MM-DD`, суммы — целые микродоллары (1e-6 USD), без плавающей точки.

Лимит в штуках сообщений врал бы: разбор месяца стоит как двадцать коротких
вопросов. Инкремент атомарный (`ai_usage_add`), потому что две вкладки иначе
затрут расход друг друга.

> Формат периода уже ломался: приложение перешло на дневной учёт, а CHECK на
> таблице остался месячным — каждая запись расхода молча проваливалась, и
> лимит не работал вовсе. Починено в `2026-08-26_daily_usage_and_premium_admin`.
> Зеркало формата — `periodKey()` в `src/lib/aiBudget.js`; расходиться им нельзя.

## Зеркала: места, где одна логика живёт в двух файлах

Дублирование ниже **намеренное** — но каждое из них надо править парой.

| Что | Где 1 | Где 2 | Почему нельзя объединить |
|---|---|---|---|
| Ранжирование тарифов | `src/lib/subscription.js` `bestTier` | представление `admin_subscriptions` | Представление не может звать JS |
| Ключ периода AI | `src/lib/aiBudget.js` `periodKey()` | CHECK на `ai_usage.period` | Формат должен совпасть побайтно |
| Видимость поста | `can_view_post()` | предикат политики `posts select` | Политика на `posts`, зовущая функцию, читающую `posts`, зациклится |
| Отбрасывание лишних полей профиля | `friend_state()` | `src/lib/friendView.js` | Второй слой на случай нового фронтенда со старой базой |

## Хранилище файлов

Два публичных на чтение бакета: `chat-images` и `post-images`.

Ограничения стоят **на стороне базы**, а не только в клиенте: 3 МБ,
`image/jpeg|png|webp`, заливка только в свою папку `{uid}/…`. До этого
ограничение «сжимаем до 1280px и JPEG» жило только в клиентском коде, то есть
не было ограничением вовсе — прямым запросом можно было залить гигабайты чего
угодно.

Бакеты публичны на чтение: у кого есть точный URL, тот увидит картинку без
проверки дружбы. URL содержит uuid и не перебирается, ссылку не отдаёт ни один
запрос без прав — но **границей доступа бакет не является**. Граница — RLS на
`posts` и `messages`.
