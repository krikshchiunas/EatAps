# Архив. Эти файлы запускать нельзя

Здесь лежат четыре файла `update_*.sql`, которыми обновляли базу летом 2026.
Каждый — **снимок уже применённых миграций**, а не отдельная работа: то же
самое лежит в `supabase/migrations/` и попадает в `setup_all.sql`.

Файлы сохранены как история, а не как инструмент. Они удалены из `SOURCES` и
не участвуют ни в одной сборке.

---

## Почему их нельзя прогонять сегодня

Они написаны через `create or replace` и `drop policy` — то есть **молча
заменяют** живые объекты своими старыми редакциями. Прогон любого из них
откатывает исправления, сделанные позже.

| Файл | Что откатит |
|---|---|
| `update_2026-08-23.sql` | Политику `app_state`: вернёт версию, которая читает `friendships` напрямую вместо `is_friend_with`. Пары, потерявшие гонку, перестанут видеть дневники друг друга. **Плюс упадёт на середине:** пересоздаёт `user_brief()` с обращением к `p.public_id` — колонки нет с `2026-08-26`, и `language sql` проверяется при создании → `42703`. Политики к этому моменту уже заменены |
| `update_2026-08-24_ai.sql` | CHECK на `ai_usage.period` обратно на месячный `'^\d{4}-\d{2}$'`. Приложение пишет дневной ключ → **каждая запись расхода проваливается**, ассистент отвечает «временно недоступен» на любой запрос |
| `update_2026-08-25_promo.sql` | `issue_promo()` без `AI_PREMIUM` (код на Premium не выпустить) и `admin_subscriptions` с месячным джойном `ai_usage` (расход показывается нулевым) и ранжированием без `AI_PREMIUM` (человек с Premium отображается как FREE) |
| `update_2026-08-26_premium_and_daily.sql` | Почти совпадает с текущим состоянием, но так же перекрывает `admin_subscriptions` и `issue_promo`. Отдельного смысла не имеет: всё это есть в миграциях |

Ни один из них не является «обновлением поверх текущей базы» — все четыре
описывают более раннее состояние.

---

## Что делать вместо них

| Задача | Чем |
|---|---|
| Поднять базу с нуля | `supabase/setup_all.sql` — целиком в SQL Editor |
| Обновить работающую базу | Прогнать новые файлы из `supabase/migrations/` по порядку, либо снова весь `setup_all.sql` (идемпотентен) |
| Посмотреть, что делала эта «обновка» | `supabase/docs/04-history.md` — таблица со всеми миграциями |

---

## Можно ли их удалить

Да. Они не нужны ни для установки, ни для обновления, и вся их содержательная
часть лежит в `migrations/`. Оставлены только на случай, если понадобится
свериться с тем, что реально прогоняли на проде в те дни — например, при
разборе базы, которую обновляли ими, а не миграциями.
